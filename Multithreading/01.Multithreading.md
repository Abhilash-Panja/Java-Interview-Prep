# Question 1: What is a process and what is a thread?

**Priority:** 🔥 Must Know
**Source:** ➕ Added — no dedicated Process-vs-Thread question in the PDF

### Difficulty

Beginner

### Interview Frequency

Very High

### Short Interview Answer

> A process is an executing program with its own runtime resources and memory space. A thread is an execution path inside a process. Threads belonging to the same process share resources such as heap memory, while each thread has its own execution stack and program counter.

Think of your Spring Boot application:

```text
              Java Process
                   |
         +---------+---------+
         |         |         |
      Thread 1  Thread 2  Thread 3
         |         |         |
      Stack      Stack      Stack
         \         |         /
          \        |        /
             Shared Heap
```

That shared heap is what makes multithreading both:

```text
powerful
and
dangerous
```

---

# Why Are Threads Useful?

Suppose a server receives:

```text
Request A
Request B
Request C
```

If one execution path handled everything:

```text
A ───────────────► complete
                  B ─────────────► complete
                                  C ─────────►
```

later requests may wait unnecessarily.

With multiple execution paths:

```text
Thread 1 → Request A
Thread 2 → Request B
Thread 3 → Request C
```

work can overlap.

# Question 2: What is multithreading?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 71

### Short Interview Answer

> Multithreading means allowing multiple threads of execution to operate within the same application. These threads may execute concurrently and, when hardware permits, possibly in parallel. Because threads can share application memory, multithreading can improve responsiveness and throughput, but shared mutable state must be coordinated carefully.

The PDF describes multithreading as executing multiple threads concurrently, notes that even a normal Java application starts with the `main` thread, and distinguishes user and daemon threads.

---

# 🔄 Clarification to the PDF

The PDF calls a thread a:

> "lightweight sub-process."

That phrase is common in interview books, but a more precise explanation is:

> A thread is an execution unit **inside a process**. Threads in the same process share many process resources.

Use that wording in interviews.

# Question 3: Concurrency vs Parallelism

**Priority:** 🔥 Important | ⚠️ Often Confused
**Source:** ➕ Added

These are related but not identical.

### Concurrency

Multiple tasks make progress during overlapping periods.

Example on one CPU core:

```text
Time →

Thread A: AAA---AAA---AAA
Thread B: ---BBB---BBB---
```

The scheduler switches between them.

They are concurrent even if only one instruction stream runs at an instant.

---

### Parallelism

Tasks actually execute simultaneously.

Example with multiple CPU cores:

```text
Core 1 → Thread A █████████

Core 2 → Thread B █████████
```

### Interview Answer

> Concurrency is about managing multiple tasks whose execution overlaps; parallelism means multiple tasks are literally executing simultaneously on different processing resources.

# Question 6: How can we create a thread in Java?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 72

The PDF presents two classic approaches:

1. Extend `Thread`
2. Implement `Runnable`



---

# Approach 1 — Extend `Thread`

```java
class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println(
                "Executing: "
                + Thread.currentThread().getName()
        );
    }
}
```

Then:

```java
MyThread thread =
        new MyThread();

thread.start();
```

---

# Approach 2 — Implement `Runnable`

```java
class MyTask implements Runnable {

    @Override
    public void run() {

        System.out.println(
                "Executing task"
        );
    }
}
```

Then:

```java
Thread thread =
        new Thread(
                new MyTask()
        );

thread.start();
```

Or using Lambda:

```java
Thread thread =
        new Thread(
            () ->
                System.out.println("Running")
        );

thread.start();
```

Notice how Module 8 connects directly here:

```text
Runnable
     ↓
Functional Interface
     ↓
Lambda
```

# Question 7: Thread vs Runnable — which is better?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 73

The PDF recommends `Runnable` because:

* extending `Thread` consumes the class's one inheritance opportunity;
* usually we want to define a **task**, not customize Thread itself;
* the Executor framework works naturally with task objects.

### Strong Interview Answer

> Usually I prefer separating the task from the mechanism executing it. `Runnable` represents the work, while `Thread` represents one execution mechanism. That gives better composition and works naturally with ExecutorService. In modern backend applications, we usually work with executors rather than manually creating raw threads for every task.

Mental model:

```text
Bad coupling:

Business Task
    IS-A
   Thread


Better:

Business Task
    IS
 Runnable
    |
    v
Execution mechanism
Thread / Executor
```

# Question 8: Difference between `start()` and `run()`

**Priority:** 🔥🔥 Must Know | ⚠️ Classic Trap
**Source:** 📘 PDF Question 74

### Short Interview Answer

> Calling `start()` requests a new thread of execution, and that new thread eventually executes the thread's `run()` method. Calling `run()` directly is just an ordinary method invocation and executes on the current thread; it doesn't create a new thread.

The PDF states exactly this distinction.

Example:

```java
Thread thread =
        new Thread(() ->
            System.out.println(
                Thread.currentThread().getName()
            )
        );
```

### Direct `run()`

```java
thread.run();
```

Likely prints:

```text
main
```

because:

```text
main thread
    ↓
ordinary method call
    ↓
run()
```

---

### `start()`

```java
thread.start();
```

might print:

```text
Thread-0
```

because:

```text
main thread
    ↓
start()
    ↓
new thread becomes schedulable
    ↓
new thread executes run()
```

# Question 9: Can a thread be started twice?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 75

No.

The PDF states that attempting to start an already-started thread results in:

```text
IllegalThreadStateException
```



Example:

```java
Thread t = new Thread(task);

t.start();

t.start(); // Runtime failure
```

A Java `Thread` object represents one thread lifecycle.

If you need another execution:

```java
new Thread(task).start();
```

or, preferably for repeated work:

```text
ExecutorService
```

# Question 10: What is the thread lifecycle?

**Priority:** 🔥🔥 Must Know
**Source:** ➕ Added — not a dedicated PDF question

Java exposes these principal `Thread.State` values:

```text
NEW
RUNNABLE
BLOCKED
WAITING
TIMED_WAITING
TERMINATED
```

Conceptually:

```text
             start()
 NEW ----------------------► RUNNABLE
                                |
             +------------------+------------------+
             |                  |                  |
          BLOCKED            WAITING          TIMED_WAITING
             |                  |                  |
             +------------------+------------------+
                                |
                                v
                           RUNNABLE
                                |
                          run() completes
                                |
                                v
                           TERMINATED
```

---

## `NEW`

```java
Thread t = new Thread(task);
```

Created but not started.

---

## `RUNNABLE`

After:

```java
t.start();
```

Java's `RUNNABLE` state covers a thread eligible/running from the JVM perspective.

Do not assume Java exposes a separate:

```text
RUNNING
```

enum state.

---

## `BLOCKED`

Waiting to acquire an intrinsic monitor.

Example:

```text
Thread A
holds lock

Thread B
tries synchronized(lock)
        ↓
     BLOCKED
```

---

## `WAITING`

Waiting indefinitely for another action.

Examples include:

```java
object.wait();

thread.join();
```

without timeout.

---

## `TIMED_WAITING`

Waiting for a limited time.

Examples:

```java
Thread.sleep(1000);

object.wait(1000);

thread.join(1000);
```

---

## `TERMINATED`

The `run()` method has completed.

# Question 11: What is a race condition?

**Priority:** 🔥🔥🔥 Must Know
**Source:** 📘 PDF discusses a producer-consumer race under Question 77; ➕ expanded here.

The PDF shows a race where condition checking and `wait()` are not correctly synchronized, allowing a notification to be missed between those operations.

### Short Interview Answer

> A race condition occurs when multiple threads access shared state and the program's result depends on their unpredictable execution ordering. If at least one thread modifies that state without proper coordination, operations can interleave in ways that produce incorrect results.

---

# Classic Example — `count++`

```java
class Counter {

    int count = 0;

    void increment() {
        count++;
    }
}
```

Now:

```text
Thread A → increment
Thread B → increment
```

Freshers think:

```text
count++
```

is one operation.

Conceptually it is closer to:

```text
1. Read count
2. Calculate count + 1
3. Write result
```

Suppose:

```text
count = 10
```

Interleaving:

```text
Thread A reads 10

Thread B reads 10

Thread A calculates 11

Thread B calculates 11

Thread A writes 11

Thread B writes 11
```

Expected:

```text
12
```

Actual:

```text
11
```

One update was lost.

---

# PDF Atomic Example

The PDF later demonstrates essentially this issue: two threads repeatedly increment the same mutable counter, and instead of reliably obtaining 100, the result varies because the operation is not safely coordinated.

That is the root problem synchronization and atomic operations solve.

# Question 12: What does `synchronized` do?

**Priority:** 🔥🔥🔥 Must Know
**Source:** 📘 PDF Question 81

### Short Interview Answer

> `synchronized` protects a critical section using an intrinsic monitor. Only a thread that owns the relevant monitor may execute that synchronized section. It provides mutual exclusion and also establishes memory-visibility guarantees when threads acquire and release the same monitor.

The PDF explains that synchronized controls access to shared resources and states that changes made while holding a lock become visible through synchronization to other threads.

---

# Root Problem

Unsafe:

```java
void increment() {
    count++;
}
```

Safe with intrinsic locking:

```java
synchronized void increment() {
    count++;
}
```

Now:

```text
Thread A
   |
 acquire lock
   |
 read + modify + write
   |
 release lock
   |
Thread B can enter
```

---

# Critical Section

You don't necessarily synchronize the entire method.

```java
void process() {

    doIndependentWork();

    synchronized (lock) {
        updateSharedState();
    }

    doMoreIndependentWork();
}
```

Why is this often preferable?

Because only:

```text
shared critical state
```

needs serialized access.

Smaller critical section:

```text
less contention
more concurrency
```

---

```java
public synchronized void update() {
}
```

locks:

```text
this
```

the current object.

Equivalent conceptually to:

```java
public void update() {

    synchronized (this) {
        ...
    }
}
```

# Why Can Two Objects Execute the Same Synchronized Method Concurrently?

Suppose:

```java
Counter c1 = new Counter();
Counter c2 = new Counter();
```

Thread A:

```java
c1.increment();
```

Thread B:

```java
c2.increment();
```

Locks:

```text
Thread A → monitor of c1

Thread B → monitor of c2
```

Different monitors.

Therefore they need not block each other.

The PDF explicitly demonstrates this with two objects: threads sharing one instance block each other, while threads using another instance hold another object lock.

# Question 14: What is static synchronization?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 82

Example:

```java
public static synchronized void update() {
}
```

The lock is associated with:

```java
ClassName.class
```

rather than one particular instance.

Conceptually:

```java
static synchronized void update()
```

is like:

```java
static void update() {

    synchronized (MyClass.class) {
        ...
    }
}
```

The PDF correctly distinguishes class-level locking from instance-level locking.

---

# 🔄 Important Precision

The PDF says static synchronization means:

> "only one thread can access the class at a time."

That's too broad.

Correct:

> Only one thread at a time can hold that particular `Class` object's monitor. Other code that doesn't acquire the same monitor can still execute.

For example:

```java
static synchronized void a() {}

static synchronized void b() {}
```

mutually exclude because both use:

```text
MyClass.class
```

But:

```java
static void c() {}
```

is unsynchronized and doesn't automatically block.

# Question 16: Is Java synchronization reentrant?

**Priority:** 🔥 Important | ⚠️ Tricky
**Source:** 📘 PDF Question 83

Yes.

The PDF states that Java intrinsic synchronization is **reentrant**: if a thread already owns a monitor and calls another synchronized method requiring that same monitor, it can enter again.

Example:

```java
class Service {

    synchronized void methodA() {
        methodB();
    }

    synchronized void methodB() {
        System.out.println("B");
    }
}
```

One thread:

```text
methodA()
   ↓
acquires this monitor
   ↓
methodB()
   ↓
same monitor already owned by same thread
   ↓
allowed
```

Without reentrancy, this would deadlock against itself.

# Question 17: Why are `wait()`, `notify()` and `notifyAll()` in `Object`?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 76

### Short Interview Answer

> They operate on an object's intrinsic monitor and wait set, not on a Thread object as such. A thread waits for a condition associated with a shared object's monitor, and another thread coordinating through that same monitor can notify waiting threads. That's why these methods belong to `Object`.

The PDF gives this same monitor-based reasoning: threads coordinate around the shared object's lock rather than needing direct knowledge of each other.

Mental model:

```text
Shared Queue Object
       |
       +---- monitor
       |
       +---- wait set
             |
        +----+----+
        |         |
     Thread A  Thread B
```

# Question 18: What exactly does `wait()` do?

**Priority:** 🔥🔥 Must Know

Suppose a thread owns:

```text
monitor M
```

and calls:

```java
M.wait();
```

Conceptually:

```text
Thread owns M
     ↓
calls wait()
     ↓
releases M
     ↓
enters waiting state
     ↓
later notified/interrupted/etc.
     ↓
must reacquire M
     ↓
continues
```

### Key Point

`wait()`:

```text
RELEASES the monitor while waiting
```

This is fundamental.

# Question 19: What does `notify()` do?

**Priority:** 🔥 Important

```java
lock.notify();
```

selects one thread waiting on that object's monitor for notification.

But an important detail:

> `notify()` does **not** instantly hand the monitor to the waiting thread.

The notifying thread still owns the monitor until it exits the synchronized section.

Then the awakened thread must compete to reacquire it.

Conceptually:

```text
Thread A holds lock
       |
   notify()
       |
Thread B becomes eligible
       |
Thread A STILL holds lock
       |
Thread A exits synchronized
       |
lock released
       |
Thread B can reacquire
```

---

# Question 20: `notify()` vs `notifyAll()`

**Priority:** 🔥 Must Know

### `notify()`

Wakes one waiting thread.

```java
lock.notify();
```

Which waiting thread?

You should not rely on a deterministic choice.

---

### `notifyAll()`

Wakes all threads waiting on that object's monitor.

```java
lock.notifyAll();
```

But they don't all enter the critical section simultaneously.

They must compete for:

```text
same monitor
```

one by one.

# Question 21: Why must `wait/notify/notifyAll` be called while owning the monitor?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 77

The PDF states that calling them without correct synchronization can cause:

```text
IllegalMonitorStateException
```

and illustrates coordination/race problems.

Correct:

```java
synchronized (lock) {
    lock.wait();
}
```

Incorrect:

```java
lock.wait();
```

without owning `lock`'s monitor.

---

# Why?

Because the operation:

```text
check condition
+
release lock
+
wait
```

must coordinate atomically with other threads modifying that condition.

Otherwise you can create a:

```text
lost notification
```

race—the scenario the PDF describes in its producer-consumer example.

# Question 22: Why should `wait()` normally be used inside a `while` loop?

**Priority:** 🔥🔥 Deep Understanding
**Source:** ➕ Added

Bad:

```java
synchronized (queue) {

    if (queue.isEmpty()) {
        queue.wait();
    }

    consume();
}
```

Better:

```java
synchronized (queue) {

    while (queue.isEmpty()) {
        queue.wait();
    }

    consume();
}
```

Why?

Because being notified does **not** guarantee:

```text
the condition I need is now true
```

Possible reasons:

```text
another consumer got the item first
spurious wakeup
different condition was notified
```

So the rule is:

```text
Wake up
   ↓
reacquire monitor
   ↓
RECHECK condition
```

# Question 23: `wait()` vs `sleep()`

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 78

The PDF gives the crucial differences: `wait()` releases the monitor and participates in inter-thread coordination, while `sleep()` pauses the current thread without releasing monitors it already owns.

| `wait()`                                    | `sleep()`                            |
| ------------------------------------------- | ------------------------------------- |
| Defined on `Object`                         | Static method on `Thread`            |
| Used for coordination                       | Used to pause execution              |
| Must own target monitor                     | No synchronized context required     |
| Releases that monitor                       | Does not release held monitors       |
| Waits for notification/interruption/timeout | Wakes after duration or interruption |

### Famous Interview Sentence

> **`wait()` releases the object's monitor; `sleep()` does not release locks the thread already holds.**

# Question 25: What is `yield()`?

**Priority:** ⭐ Important | ⚠️ Tricky
**Source:** 📘 PDF Question 80

The PDF describes `yield()` as giving other runnable threads an opportunity to execute.

### Stronger Current Answer

> `Thread.yield()` is only a scheduling hint that the current thread is willing to yield its current use of the processor. The scheduler is free to ignore it, so application correctness must never depend on `yield()`.

### 🔄 Correction

The PDF says `yield()`:

> "guarantees that CPU will be relinquished."

Do **not** memorize that.

There is no useful scheduling guarantee you should depend on.

# Question 26: What is deadlock?

**Priority:** 🔥🔥 Must Know | ⚠️ Classic Interview Question
**Source:** ➕ Added — no dedicated `deadlock` question was found in the PDF's multithreading section.

### Short Interview Answer

> Deadlock occurs when two or more threads are permanently waiting for resources held by one another, so none of them can make progress.

Example:

```text
Thread A:
holds Lock 1
waits for Lock 2


Thread B:
holds Lock 2
waits for Lock 1
```

Diagram:

```text
Thread A ──holds──► Lock 1
   ▲                  |
   |                  |
 waits              waits
   |                  |
 Lock 2 ◄──holds── Thread B
```

Nobody can proceed.

---

# Code Example

```java
Object lockA = new Object();
Object lockB = new Object();
```

Thread 1:

```java
synchronized (lockA) {

    synchronized (lockB) {
        // work
    }
}
```

Thread 2:

```java
synchronized (lockB) {

    synchronized (lockA) {
        // work
    }
}
```

Potential deadlock.

---

# How Do We Prevent It?

One common strategy:

```text
always acquire locks
in a consistent global order
```

For example, every thread:

```text
Lock A
   ↓
Lock B
```

Never one thread:

```text
A → B
```

while another uses:

```text
B → A
```

Other approaches include:

```text
reduce nested locking
use higher-level concurrent abstractions
use timed lock attempts where appropriate
minimize shared mutable state
```

# Question 27: What is `volatile`?

**Priority:** 🔥🔥🔥 Must Know | ⚠️ Frequently Misunderstood
**Source:** 📘 PDF Question 68 + modernization

The PDF says `volatile` can be applied to variables and emphasizes visibility between threads, explaining it using the traditional "main memory vs thread-local cached value" model.

### Short Interview Answer

> `volatile` is used for a variable shared between threads when we need visibility and ordering guarantees without mutual-exclusion locking. A write to a volatile variable happens-before a subsequent read of that same variable. However, volatile does not make compound operations such as `count++` atomic.

That final sentence is extremely important.

---

# The Problem `volatile` Solves

Imagine:

```java
boolean running = true;
```

Thread A:

```java
while (running) {
    // work
}
```

Thread B:

```java
running = false;
```

Without the required memory-visibility relationship, Thread A may not be guaranteed to observe the update in the way your program needs.

Use:

```java
volatile boolean running = true;
```

Now:

```text
Thread B
writes false
      ↓
volatile write
      ↓
happens-before
      ↓
later volatile read
      ↓
Thread A observes update
```

---

# 🔄 Better Than the "Always Read Main Memory" Story

The PDF explains volatile as threads reading/writing directly to:

```text
main memory
```

instead of caches.

That is a useful introductory analogy, but for an interview the safer formulation is:

> `volatile` gives Java Memory Model visibility and ordering guarantees through happens-before semantics.

Don't make promises about literal CPU-cache bypass behavior.

---

No.

```java
volatile int count = 0;
```

and:

```java
count++;
```

is still conceptually:

```text
read
 ↓

 ↓

```


# Question 29: What does atomicity mean?

**Priority:** 🔥🔥 Must Know
**Source:** ➕ Added

An atomic operation behaves as one indivisible action with respect to competing threads.

Other threads cannot observe/interleave with a partially completed operation in the relevant sense.

Example requirement:

```text
increment count exactly once
```

Unsafe compound operation:

```java
count++;
```

Safe alternatives might include:

```java
synchronized void increment() {
    count++;
}
```

or:

```java
AtomicInteger count =
        new AtomicInteger();
```

# Question 47: What is `CyclicBarrier`?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 92

### Short Interview Answer

> `CyclicBarrier` allows a fixed number of participating threads to wait for each other at a common barrier. Once all parties reach the barrier, they are released and the barrier can be used again for another cycle.

The PDF describes participants as parties and explains that each calls `await()` until all parties arrive.

Example:

```text
Thread A ----work----► barrier
                         |
Thread B ------work----► barrier
```

# 🔄 Correction to PDF Reuse Explanation

The PDF says CyclicBarrier is reusable:

> "by calling `reset()`."

Better answer:

> After a barrier is successfully tripped, `CyclicBarrier` automatically moves to the next generation and can be reused. `reset()` explicitly resets the barrier, for example when recovering/resetting its state; it isn't required after every successful cycle.

# Interviewer Grill Round — Multithreading

Now imagine the actual interview.

---

### Interviewer

What is a thread?

### Candidate

A thread is an execution path inside a process. Threads in the same process share process resources such as heap memory but maintain their own execution stacks.

---

### Interviewer

What is multithreading?

### Candidate

It's allowing multiple execution threads within an application to make progress concurrently, potentially in parallel when hardware resources allow it.

---

### Interviewer

Concurrency vs parallelism?

### Candidate

Concurrency means multiple tasks make progress during overlapping time periods. Parallelism means multiple tasks are actually executing simultaneously on different processing resources.

---

### Interviewer

How do you create a thread in Java?

### Candidate

The traditional approaches are extending Thread or implementing Runnable and passing it to a Thread. In application code I normally prefer separating the task from its execution mechanism and often use executors instead of raw threads.

---

### Interviewer

Why Runnable over Thread?

### Candidate

Runnable models the task without tying it to one execution mechanism, preserves normal class inheritance, and works naturally with Executor APIs.

---

### Interviewer

Difference between:

```java
t.start();
```

and:

```java
t.run();
```

### Candidate

`start()` arranges for the task to execute on a new thread. Calling `run()` directly is only a normal method call on the current thread.

---

### Interviewer

Can I start the same Thread twice?

### Candidate

No. Attempting to start an already-started Thread throws `IllegalThreadStateException`.

---

### Interviewer

What are the thread states?

### Candidate

`NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, and `TERMINATED`.

---

### Interviewer

What is a race condition?

### Candidate

It's when multiple threads access shared state and the correctness depends on unpredictable timing or interleaving, typically because shared mutable state is not coordinated correctly.

---

### Interviewer

Why isn't `count++` thread-safe?

### Candidate

Because it's a read-modify-write sequence rather than one indivisible operation. Two threads can read the same old value and overwrite one another's updates.

---

### Interviewer

Then make it volatile.

### Candidate

Volatile would solve visibility of the count but not make the read-modify-write increment atomic. I would need synchronization or an atomic operation such as `AtomicInteger.incrementAndGet()`.

---

### Interviewer

What does synchronized provide?

### Candidate

Mutual exclusion for threads using the same monitor plus memory-visibility and ordering guarantees associated with monitor release and acquisition.

---

### Interviewer

What does this lock?

```java
synchronized void update()
```

### Candidate

The current instance, effectively `this`.

---

### Interviewer

And:

```java
static synchronized void update()
```

### Candidate

The `Class` object representing that class.

---

### Interviewer

Can those two methods execute concurrently?

### Candidate

Potentially yes, because one uses the instance monitor and the other uses the Class monitor, which are different locks.

---

### Interviewer

Can a synchronized method call another synchronized method on the same object?

### Candidate

Yes. Java intrinsic monitors are reentrant, so the current thread can reacquire the monitor it already owns.

---

### Interviewer

Why is `wait()` defined in Object?

### Candidate

Because waiting and notification are associated with an object's monitor and wait set. Threads coordinate around the shared object's monitor, not by directly waiting on another Thread object.

---

### Interviewer

What happens when `wait()` is called?

### Candidate

The current thread must own that monitor, then it releases the monitor and enters a waiting state. Before returning from wait, it must reacquire the monitor.

---

### Interviewer

Difference between `wait()` and `sleep()`?

### Candidate

Wait is monitor-based inter-thread coordination and releases the target monitor. Sleep simply pauses the current thread for a period and doesn't release monitors the thread already owns.

---

### Interviewer

Does `notify()` release the lock?

### Candidate

No. It notifies a waiter, but the notifying thread retains the monitor until it exits the synchronized region.

---

### Interviewer

Why should `wait()` be inside `while`, not `if`?

### Candidate

Because after waking and reacquiring the lock, the required condition may no longer be true, and spurious wakeups are also possible. The condition must therefore be rechecked.

---

### Interviewer

What is deadlock?

### Candidate

A situation where threads wait indefinitely for resources held by one another, such as thread A holding lock 1 and waiting for lock 2 while thread B holds lock 2 and waits for lock 1.

---

### Interviewer

How would you avoid that example?

### Candidate

A common strategy is enforcing one consistent global lock-acquisition order, while also minimizing nested locking and shared mutable state.

---

### Interviewer

What is volatile?

### Candidate

It gives visibility and ordering guarantees for accesses to that variable through Java Memory Model happens-before semantics, but it doesn't provide mutual exclusion or make compound operations atomic.

---

### Interviewer

Give me a good volatile use case.

### Candidate

A simple shared state flag such as a shutdown indicator where one thread writes the flag and others read it.

---

### Interviewer

What are atomic classes?

### Candidate

Classes such as `AtomicInteger` provide atomic operations on individual values, including operations such as increment and compare-and-set, without requiring a synchronized block for each operation.

---

### Interviewer

Runnable vs Callable?

### Candidate

Runnable's `run()` returns void and can't declare checked exceptions. Callable's `call()` returns a value and may throw checked exceptions.

---

### Interviewer

Callable returns Future, right?

### Candidate

No. `Callable<V>.call()` returns `V`. When I submit that Callable to an ExecutorService, `submit()` returns `Future<V>`.

🔥 Excellent counter-question.

---

### Interviewer

What is Future?

### Candidate

It represents the eventual result of an asynchronous task. I can check or obtain the result, cancel the task, and retrieve failures. `get()` blocks if the result isn't ready.

---

### Interviewer

Why Executors?

### Candidate

They separate tasks from thread management and allow controlled worker pools, thread reuse, task queues, lifecycle management, and result handling.

---

### Interviewer

FixedThreadPool vs CachedThreadPool?

### Candidate

A fixed pool limits worker count and queues excess work, whereas a cached pool can create additional workers as needed and is better suited only when its unbounded growth characteristics are appropriate for short-lived workloads.

---

### Interviewer

What happens after `shutdown()`?

### Candidate

The executor stops accepting new tasks but continues processing tasks already submitted.

---

### Interviewer

What about `shutdownNow()`?

### Candidate

It attempts to interrupt active tasks and initiate a quicker shutdown, but it doesn't guarantee that running tasks instantly stop because interruption is cooperative.

---

### Interviewer

CountDownLatch vs CyclicBarrier?

### Candidate

CountDownLatch is typically one-way: threads count down events and waiters proceed once the count reaches zero, after which it cannot be reused. CyclicBarrier is a reusable rendezvous where a fixed number of participating threads wait for one another at the same barrier point.
