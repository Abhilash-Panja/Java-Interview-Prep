# Java OOP — Encapsulation Through Bookings

We have learned how to create bookings and initialize their details. Now we need to control how an existing booking changes.

## 1. Start with the booking rule

Imagine that your ride is confirmed. You can either start the ride or cancel the booking.

For this lesson, we choose the following business rules:

| Current status | Requested operation | Result |
|---|---|---|
| CONFIRMED | Start the ride | Change to STARTED |
| CONFIRMED | Cancel the booking | Change to CANCELLED |
| STARTED | Cancel the booking | Reject the request |
| CANCELLED | Start the ride | Reject the request |

These are simplified rules for our demonstration. Both operations require the current status to be `CONFIRMED`, so repeating either operation after it succeeds is also rejected.

The central requirement is: **callers should request an operation, and the booking implementation should check whether that operation is allowed.**

## 2. A booking-office example

Suppose the office keeps an official record for each booking. If employees can freely erase and rewrite its status, someone might mark an ongoing ride as cancelled.

A controlled process makes employees submit a cancellation request. The booking desk checks the current status before updating the record.

The software equivalent is to keep the state inside the booking object and expose operations that enforce the rules. The object follows code we write; it does not make independent decisions.

## 3. Exposed fields let callers bypass the process

Consider this deliberately exposed design:

```java
class BookingData {
    public String status = "CONFIRMED";
}
```

Code elsewhere can write:

```java
// Statements inside a caller's method:
BookingData booking = new BookingData();
booking.status = "STARTED";
booking.status = "CANCELLED";
```

Java accepts the assignments, even though the second status change breaks our booking rule. No business-rule check runs when a caller directly assigns the field.

## 4. A private field is a useful boundary

We can stop direct access from ordinary calling code by making the field private:

```java
private String status;
```

In our complete example below, `Main` cannot directly assign to `booking.status`; the compiler rejects that access. Java's access modifiers control which code can access a class member. [Official Java guide to access control](https://dev.java/learn/classes-objects/more-on-classes/).

However, the operations we expose must also respect the rules.

## 5. An unrestricted setter still allows the invalid change

Suppose we expose this method:

```java
// An unrestricted setter: this would allow arbitrary status assignments.
public void setStatus(String status) {
    this.status = status;
}
```

A caller could then write:

```java
booking.setStatus("STARTED");
booking.setStatus("CANCELLED");
```

The field is private, but the method still allows a forbidden transition.

Even checking that `"CANCELLED"` is a recognized status would not be enough. We must also check whether cancellation is permitted from the current status.

Setters can be useful for suitable properties, and they can validate inputs. The issue here is that an unrestricted status setter exposes changes that our booking rules forbid.

## 6. Expose operations that enforce the rules

Instead, give the class operations such as `startRide()` and `cancel()`:

```java
// Status-handling methods inside Booking:
public void startRide() {
    if (!"CONFIRMED".equals(status)) {
        throw new IllegalStateException(
            "Only confirmed bookings can start."
        );
    }

    status = "STARTED";
}

public void cancel() {
    if (!"CONFIRMED".equals(status)) {
        throw new IllegalStateException(
            "Only confirmed bookings can be cancelled."
        );
    }

    status = "CANCELLED";
}
```

The caller requests an operation:

```java
booking.cancel();
```

The booking method checks its own current state and changes it only when allowed.

Encapsulation brings related data and behavior together behind a defined interface. Controlling access to internal state lets the implementation manage how it is used and changed. [Official Java introduction to encapsulation](https://dev.java/learn/oop/).

In this example, that interface is the set of methods callers use. We do not need Java's `interface` keyword to demonstrate encapsulation.

## 7. Read the condition and rejection carefully

In this expression:

```java
!"CONFIRMED".equals(status)
```

`equals` compares the text values, and `!` reverses the Boolean result. Read it as: *the current status is not CONFIRMED.*

`throw new IllegalStateException(...)` rejects the request by throwing an exception. Execution leaves the method before the following assignment can run. It does not undo earlier changes, so the check must happen before the state change in this example.

The try/catch in the demonstration below prints the rejection and lets the program continue. The exception mechanism is supporting syntax here; the design idea is that a forbidden operation must not change the status.

## 8. Run the complete example

This class keeps the overloaded and chained constructors from our earlier lesson. They establish the initial status; the operation methods control later transitions.

Save the following as `Main.java`:

```java
public class Main {
    public static void main(String[] args) {
        Booking abhilashBooking = new Booking(101, "Abhilash");
        Booking raviBooking = new Booking(102, "Ravi", "PREMIUM");

        abhilashBooking.startRide();
        raviBooking.cancel();

        System.out.println("Abhilash: " + abhilashBooking.getStatus());
        System.out.println("Ravi: " + raviBooking.getStatus());

        try {
            abhilashBooking.cancel();
        } catch (IllegalStateException exception) {
            System.out.println("Rejected: " + exception.getMessage());
        }

        System.out.println("Abhilash after rejected cancellation: "
            + abhilashBooking.getStatus());
    }
}

class Booking {
    private int bookingId;
    private String passengerName;
    private String rideType;
    private String status;

    public Booking(int bookingId, String passengerName) {
        this(bookingId, passengerName, "STANDARD");
    }

    public Booking(int bookingId, String passengerName, String rideType) {
        this.bookingId = bookingId;
        this.passengerName = passengerName;
        this.rideType = rideType;
        this.status = "CONFIRMED";
    }

    public void startRide() {
        if (!"CONFIRMED".equals(status)) {
            throw new IllegalStateException(
                "Only confirmed bookings can start."
            );
        }

        status = "STARTED";
    }

    public void cancel() {
        if (!"CONFIRMED".equals(status)) {
            throw new IllegalStateException(
                "Only confirmed bookings can be cancelled."
            );
        }

        status = "CANCELLED";
    }

    public String getStatus() {
        return status;
    }

    public void showDetails() {
        System.out.println(
            bookingId + " | " + passengerName + " | "
            + rideType + " | " + status
        );
    }
}
```

With a JDK installed, run:

```bash
javac Main.java
java Main
```

Output:

```
Abhilash: STARTED
Ravi: CANCELLED
Rejected: Only confirmed bookings can be cancelled.
Abhilash after rejected cancellation: STARTED
```

The two valid operations succeed on separate bookings. The later cancellation request for the started booking fails, and its status remains `STARTED`.

## 9. Connect each part to its responsibility

| Part of the design | Responsibility |
|---|---|
| Constructor | Establish the initial `CONFIRMED` status |
| Private `status` field | Prevent direct status access from `Main` |
| `startRide()` | Allow a confirmed booking to start |
| `cancel()` | Allow a confirmed booking to be cancelled |
| `getStatus()` | Let callers read the status |
| Checks before assignments | Reject forbidden transitions before changing state |

We expose a getter because callers need to inspect the status. There is no need to offer an unrestricted setter just because a getter exists.

## 10. Why this helps as the application grows

The application might receive cancellation requests from a passenger screen, a support tool, or an administration screen. When those requests use the booking's cancellation operation, they go through its transition check.

If the policy changes, the implementation of that operation is a clear place to inspect and update. The caller can continue asking for a cancellation according to the operation's contract.

This guarantee depends on the actual design: code that bypasses the object and edits a database directly would not run this method. Our demonstration also uses sequential in-memory operations; handling concurrent requests requires additional coordination.

`private` controls access in program code. It does not encrypt data or decide whether an application user is authorized to cancel a particular booking.

## 11. Explain it in an interview

> Encapsulation brings related state and behavior together behind a defined interface. It helps the object control access to its internal state and enforce its rules. For example, a booking can keep its status private and expose a cancellation method that rejects cancellation after the ride starts. Making fields private is useful, but an unrestricted setter could still let callers bypass the intended rules.

**Follow-up:** Is encapsulation just getters and setters?

> No. The public operations should fit the object's responsibilities and preserve its rules. A getter can be useful, while some fields should have no public setter. A validated setter may be appropriate for other properties.

**Follow-up:** Does having a class automatically guarantee encapsulation is well designed?

> No. The class's access boundaries and behavior must be designed deliberately. Correct validation must cover the allowed operations.
