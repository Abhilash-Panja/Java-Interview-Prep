# Java OOP — Abstraction Through Bookings

Let's learn abstraction, using the same booking cancellation example.


## 1. Start with the passenger's point of view

Imagine you are writing the code behind a passenger's **Cancel Ride** button.

Your goal is simple:

> "Cancel this booking."

Should the button's code need to know:

- Which field stores the booking status?
- How the status is represented internally?
- Which internal helper performs validation?
- Exactly how the booking updates its fields?

If every caller depends on these details, changes inside `Booking` can force changes throughout the application.

**Abstraction lets callers use a meaningful operation without depending on unnecessary implementation details.**

The calling code can simply request:

```java
booking.cancel();
```

## 2. The booking-desk analogy

Think of visiting a booking desk and saying:

> "Please cancel booking 101."

You need to understand whether cancellation is allowed and whether it succeeded. You do not need to know the employee's internal record format or every administrative step.

The Java method provides a similar separation.

However, the caller still needs to understand the operation's **contract**.

## 3. What is a contract?

A contract means the behavior the caller can rely on.

For our `cancel()` method:

| Situation | Promised behavior |
|---|---|
| Booking is `CONFIRMED` | Change its status to `CANCELLED` |
| Booking has another status | Throw `IllegalStateException` |
| Cancellation is rejected | Leave the existing status unchanged |

These rules matter to the caller. They are part of what the operation means.

## 4. Look at the implementation

Now look at the implementation inside `Booking`:

```java
public void cancel() {
    ensureCancellationAllowed();
    status = "CANCELLED";
}

private void ensureCancellationAllowed() {
    if (!"CONFIRMED".equals(status)) {
        throw new IllegalStateException(
            "Only confirmed bookings can be cancelled."
        );
    }
}
```

The caller uses:

```java
booking.cancel();
```

Internally, `cancel()`:

1. Calls the validation helper.
2. Changes the status if validation succeeds.
3. Lets the exception reach the caller if validation fails.

Java objects expose operations through their methods, giving other code an interface through which to use them. [Official Java explanation](https://dev.java/learn/oop/).

## 5. What each side knows

Notice the difference between what each side knows:

| Calling code needs to know | Booking handles internally |
|---|---|
| Call `cancel()` to request cancellation | Which helper performs the check |
| Cancellation requires a confirmed booking | How the comparison is written |
| Rejection produces an exception | How the status is stored |
| Successful cancellation changes the status | Which field receives the new value |

**The caller knows the behavior; the implementation manages the details.**

## 6. See it in action

For example, inside `main()`:

```java
Booking booking = new Booking(101, "Abhilash");

booking.cancel();

System.out.println(booking.getStatus());
```

Output:

```
CANCELLED
```

This code never calls `ensureCancellationAllowed()` or directly changes the status field.

## 7. Changing the implementation without breaking callers

Now suppose we rename the private helper:

```java
private void validateCancellation() {
    // The same validation logic.
}
```

After updating the call inside `cancel()`, the caller can still write:

```java
booking.cancel();
```

Its code needs no change because the operation's contract remains the same.

Keeping the method name alone is not enough, though. If we change which bookings can be cancelled or how failures are reported, callers may need to adapt.

## 8. How is this different from encapsulation?

The same `Booking` class demonstrates both:

| Concept | Focus | Booking example |
|---|---|---|
| **Abstraction** | What operation and behavior should the caller depend on? | Use `cancel()` and understand its contract |
| **Encapsulation** | How does the implementation control access to its data and maintain its rules? | Keep `status` private and change it through guarded methods |

The private helper supports the implementation. The useful abstraction is the cancellation operation and its meaning.

Also, abstraction does not require the `abstract` keyword. Our ordinary `Booking` class already provides it. Abstract classes and interfaces are additional Java tools we will study later.

## 9. Explain it in an interview

> Abstraction exposes essential operations and their behavior while hiding unnecessary implementation details from callers. For example, calling code can use `booking.cancel()` and understand when it succeeds or fails without knowing the internal field representation or helper methods.
