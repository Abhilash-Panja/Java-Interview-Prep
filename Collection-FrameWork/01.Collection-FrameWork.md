## Question 1: What is the Java Collections Framework?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 94

**Difficulty:** Beginner
**Interview Frequency:** Very High

### Short Interview Answer

The Java Collections Framework is a set of interfaces, implementations, and utility algorithms used to store and manipulate groups of objects. Interfaces such as `List`, `Set`, and `Queue` describe collection behavior, classes such as `ArrayList`, `HashSet`, and `LinkedList` provide implementations, and utility classes such as `Collections` provide common algorithms.

The PDF defines it as an architecture for storing and manipulating groups of objects and notes that `Collection` extends `Iterable`.

### Why Do We Need a Collections Framework?

Imagine Java gave us only arrays:

```java
Employee[] employees = new Employee[100];
```

Problems:

- Fixed capacity
- Manual insertion/removal logic
- Manual sorting
- Manual searching
- No standard Set behavior
- No key-value structure
- No reusable algorithms

Instead Java gives us abstractions:

```java
List<Employee> employees = new ArrayList<>();

Set<String> usernames = new HashSet<>();

Map<Long, User> users = new HashMap<>();
```

Now we can choose the data structure based on the requirement.

## Question 3: Collection vs Collections

**Priority:** 🔥 Must Know | ⚠️ Classic Fresher Trap
**Source:** 📘 PDF Question 95

### Short Interview Answer

`Collection` is an interface at the root of much of the collection hierarchy, while `Collections` is a utility class containing static helper methods for working with collections, such as sorting, reversing, searching, and creating unmodifiable views.

The PDF describes `Collections` as a utility class and mentions methods such as `sort()` and `unmodifiableList()`.

Example:

```java
List<Integer> numbers =
        new ArrayList<>();
```

`List` ultimately belongs to the `Collection` hierarchy.

But:

```java
Collections.sort(numbers);
```

uses the utility class.

Remember:

```
Collection
→ interface

Collections
```

## Question 4: What is the difference between List, Set and Map?

### List

Use when:

- ordering matters
- duplicates are allowed
- index-based access may matter

Example:

```java
List<String> names =
        new ArrayList<>();

names.add("A");
names.add("B");
names.add("A");
```

Valid:

```
[A, B, A]
```

### Set

Use when:

- uniqueness matters

Example:

```java
Set<String> emails =
        new HashSet<>();
```

Adding the same logical element twice does not create two Set entries.

### Map

Use when:

- key → value association matters

Example:

```java
Map<Long, User> users =
        new HashMap<>();
```

Conceptually:

```
101 → User A
102 → User B
103 → User C
```

| Requirement | Choose |

## Question 5: What is ArrayList?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 96

The PDF describes `ArrayList` as a resizable-array implementation of `List`, maintaining insertion order, allowing duplicates and nulls, supporting index-based access, and not being synchronized.

### Short Interview Answer

`ArrayList` is a resizable-array implementation of the `List` interface. Internally it maintains an array-like backing structure, which makes index-based access fast. When its backing storage is insufficient, it allocates a larger array and copies existing references into it.

Example:

```java
List<String> skills =
        new ArrayList<>();

skills.add("Java");
skills.add("Spring");
skills.add("SQL");
```

## Question 6: Which data structure does ArrayList use internally?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 98

The PDF shows:

```java
transient Object[] elementData;
```

as the backing storage.

### Interview Answer

Conceptually, `ArrayList` uses a dynamically resized array as its backing storage. In the implementation examined by the PDF, that backing field is an `Object[]` named `elementData`.

Conceptually:

```
ArrayList

index   0       1       2       3
      +-------+-------+-------+-------+
      | ref A | ref B | ref C | null  |
      +-------+-------+-------+-------+
```

This explains why:

```java
list.get(2);
```

can be performed efficiently.

### 🔄 Important Correction to the PDF Wording

The PDF says `ArrayList` allocates a "contiguous block of memory" for its elements.

For interview purposes, say this more carefully:

`ArrayList` uses an array of element references, giving array-style indexed access. We should not make strong assumptions about the physical placement of the referenced Java objects themselves in memory.

The array stores references conceptually like:

```
elementData
  |
  +---- ref ----> Employee A
  |
  +---- ref ----> Employee B
  |
  +---- ref ----> Employee C
```

The Employee objects themselves aren't required to sit physically next to one another.

## Question 7: What is the default capacity of an ArrayList?

**Priority:** 🔥 Important | ⚠️ Tricky
**Source:** 📘 PDF Questions 97–99

The PDF says the default capacity is 10, but then correctly shows that the default constructor initially uses an empty backing array and expands to the default capacity when the first element is inserted.

### Better Interview Answer

The commonly discussed default capacity is 10, but a default-constructed `ArrayList` does not immediately allocate storage for ten elements. Modern implementations start with an empty backing array and allocate capacity when the first element is added.

Avoid simply saying:

"new ArrayList creates an array of size 10 immediately."

## Question 8: How does ArrayList.add() work internally?

**Priority:** 🔥🔥 Must Know | 🧠 Internal Working
**Source:** 📘 PDF Question 99

The source traces the internal flow through capacity checking and growth.

Conceptually:

```java
list.add(element);
```

does:

```
1. Check whether backing array has space
2. If yes:
      place element at next index
3. If no:
      allocate larger backing array
      copy existing references
      add new element
4. Increase logical size
```

### How Does ArrayList Grow?

The implementation examined in the PDF uses:

```
newCapacity =
oldCapacity + oldCapacity / 2
```

approximately:

```
1.5 × old capacity
```

Example:

```
10
 ↓
15
 ↓
22
...
```

The exact implementation should not be treated as an eternal language guarantee, but dynamic resizing through a larger backing array is the important concept.

## Question 9: What are ArrayList time complexities?

**Priority:** 🔥 Must Know

The PDF gives the following reasoning.

### get(index)

```
O(1)
```

because indexed access is direct.

### add(element) at end

Typically:

```
amortized O(1)
```

Occasional resize:

```
O(n)
```

because elements/references must be copied.

### Insert in middle

```
O(n)
```

because elements must shift.

```
A B C D
    ↑
 insert X

A B X C D
```

C and D move.

### Remove from middle

Also:

```
O(n)
```

because elements to the right shift left.

### What Does "Amortized O(1)" Mean?

This is a nice follow-up.

Most appends:

```
cheap
cheap
cheap
cheap
```

Occasionally:

```
EXPENSIVE resize + copy
```

But averaged across many additions:

```
average cost per append ≈ constant
```

Hence:

```
amortized O(1)
```

## Question 10: Does final ArrayList mean immutable ArrayList?

**Priority:** 🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF Question 100

The PDF explicitly demonstrates that declaring the list reference `final` does not prevent adding elements; it only prevents reassignment of that reference.

Example:

```java
final List<String> names =
        new ArrayList<>();

names.add("A");   // valid
```

But:

```java
names = new ArrayList<>(); // invalid
```

So:

```
final reference
      ≠
immutable collection
```

### Collections.unmodifiableList()

```java
List<String> original =
        new ArrayList<>();

List<String> view =
        Collections.unmodifiableList(original);
```

Important:

```
view cannot modify list directly
```

but if:

```java
original.add("Java");
```

the unmodifiable view reflects the change.

The PDF explicitly highlights this distinction.

Modern factory methods such as:

```java
List.of("Java", "Spring")
```

are another commonly used option; the PDF also mentions `List.of()` as a Java 9 addition.

## Question 11: What is LinkedList?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 101

The PDF describes Java's `LinkedList` as a doubly-linked structure using nodes containing:

```
previous
item
next
```

### Short Interview Answer

`LinkedList` implements `List` and `Deque` and internally represents elements through a doubly linked node structure. Each node keeps the item plus references to neighboring nodes. This makes sequential traversal natural, while index-based random access is slower than `ArrayList`.

Conceptually:

```
null
 ↑
[prev|A|next]
       ⇅
[prev|B|next]
       ⇅
[prev|C|next]
              ↓
             null
```

### Internal Node

The PDF shows a node structure conceptually equivalent to:

```java
class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}
```

## Question 12: What are LinkedList time complexities?

**Priority:** 🔥 Must Know

### Indexed get(index)

```
O(n)
```

because the structure must traverse nodes rather than directly indexing an array.

### Add/remove when node/location is already known

Link modification itself can be:

```
O(1)
```

Example:

```
Before:

A ⇄ B ⇄ C


Remove B:

A ⇄ C
```

just links change.

But there is an important nuance that the PDF itself acknowledges:

Finding the target index can still take O(n).

So don't blindly say:

"LinkedList insertion is always O(1)."

Better:

Link manipulation is O(1) once the insertion/removal position is known, but locating a position by index can be O(n).

## Question 13: ArrayList vs LinkedList

**Priority:** 🔥🔥 Must Know | ⚠️ Common Interview Question
**Source:** 📘 PDF Question 102

The PDF recommends `ArrayList` for frequent indexed/search-style access and `LinkedList` when repeated insertion/removal behavior is important.

### Interview Comparison

| Feature | ArrayList | LinkedList |
|---|---|---|
| Internal model | Resizable array | Doubly linked nodes |
| get(index) | O(1) | O(n) |
| Append | amortized O(1) | O(1) |
| Insert middle | O(n) shift | O(1) linking after node found |
| Find middle node | Direct index | O(n) |
| Memory overhead | Lower | Higher per element |
| Cache friendliness | Usually better | Usually worse |
| Implements Deque | No | Yes |

### Strong Interview Decision

For most ordinary `List` use cases, `ArrayList` is the default choice. `LinkedList` becomes useful when its deque operations or known-position link insertion/removal characteristics match the requirement.

## Question 14: What is HashMap?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 103

### Short Interview Answer

`HashMap` is a `Map` implementation that stores key-value pairs using hashing. A key's hash information helps determine where to look, and equality checking identifies the matching logical key. It generally provides expected constant-time `put()` and `get()` when hashing distributes keys effectively.

The PDF states that `HashMap` stores key-value pairs and provides expected constant-time `get()`/`put()` when `equals()` and `hashCode()` are implemented appropriately.

Important characteristics from the PDF:

- Unique keys
- One null key
- Multiple null values
- No guaranteed insertion order
- Not synchronized
- Default load factor 0.75

## Question 15: How does HashMap.put() work internally?

**Priority:** 🔥🔥🔥 Must Know
**Source:** 📘 PDF Question 104

This is one of the most important Java interview questions.

Suppose:

```java
map.put(key, value);
```

Simplified flow:

```
key
 ↓
hashCode()
 ↓
HashMap hash processing
 ↓
bucket index
 ↓
Is bucket empty?
 ├── Yes → insert entry
 │
 └── No
       ↓
     compare candidates
       ↓
     same logical key?
       ├── Yes → replace value
       └── No  → add another entry
```

The PDF explains the same sequence: calculate hash/bucket, then use hash/equality to decide whether to replace an existing mapping or add another entry.

### Simplified Data Structure

The implementation discussed in the PDF uses something conceptually like:

```java
Node<K,V>[] table;
```

where each node stores:

```
hash
key
value
next
```

Conceptually:

```
table

[0] → null

[1] → Node(K1,V1)
           ↓
       Node(K2,V2)

[2] → Node(K3,V3)

[3] → null
```

Each array location is commonly called a:

```
bucket
or
bin
```

## Question 16: How does HashMap.get() work?

**Priority:** 🔥🔥 Must Know

Suppose:

```java
map.get(key);
```

Simplified:

```
1. Compute key hash information
2. Determine bucket
3. Inspect candidate entries
4. Compare key equality
5. Return corresponding value if found
```

The PDF describes this lookup flow explicitly.

### Why Both hashCode() and equals()?

Recall Module 3:

```
hashCode()
    ↓
helps locate candidate bucket

equals()
    ↓
confirms logical key match
```

If:

```
e1.equals(e2) == true
```

then:

```
e1.hashCode() == e2.hashCode()
```

must also hold.

## Question 17: What is a HashMap collision?

**Priority:** 🔥🔥 Must Know

### Short Interview Answer

A collision occurs when multiple keys end up mapping to the same HashMap bucket. HashMap then needs to store and distinguish multiple entries in that bucket, using key equality when searching among candidates.

Conceptually:

```
Key A
  \
   \
    → bucket 5
   /
  /
Key B
```

Both end at:

```
bucket 5
```

### 🔄 Small Correction to the PDF

The PDF says a collision occurs because of a "poor hashCode implementation."

Poor hash functions can certainly produce too many collisions.

But collisions themselves are normal and unavoidable in hashing because many possible keys must map into a finite number of buckets.

So a stronger interview answer is:

Collisions are expected in hash tables. A poor hash distribution increases their frequency and hurts performance.

## Question 18: How are collisions handled?

**Priority:** 🔥🔥 Must Know

Initially, colliding entries can be represented in a linked structure:

```
bucket 5
   |
   v
[K1,V1]
   |
   v
[K2,V2]
   |
   v
[K3,V3]
```

Searching such a chain can become:

```
O(n)
```

for a heavily-collided bucket.

The PDF explains that Java 8 introduced tree-based handling for sufficiently large bins to improve lookup behavior toward O(log n).

## Question 19: What is HashMap treeification?

**Priority:** 🔥 Important | 🧠 Internal Working

The PDF gives:

```java
TREEIFY_THRESHOLD = 8;
```

But there is an important interview nuance.

Do not memorize:

"The instant there are exactly 8 nodes, HashMap always converts the bucket into a tree."

Modern `HashMap` also considers overall table capacity. When the table is still too small, resizing may be preferred rather than immediate treeification.

So the safe fresher answer is:

In Java 8+, heavily collided buckets may be transformed from a linked representation into a balanced tree representation after the treeification threshold and other implementation conditions are met.

**Priority:** 🔥 Must Know

The PDF identifies:

```
default initial capacity = 16

```

for `HashMap`.

### Load Factor

Conceptually:

```
threshold =
capacity × loadFactor
```

For:

```
16 × 0.75 = 12
```

once growth crosses the relevant threshold, the table resizes.

### Why Not Load Factor = 1?

Trade-off:

```
higher utilization
        vs
more collisions
```

A lower load factor uses more space but can reduce crowding.

0.75 is a compromise between:

```
memory usage
```

and

```
lookup performance
```

## Question 22: What happens if only equals() is overridden?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 105

The PDF devotes multiple pages to four custom-key scenarios.

If only `equals()` is custom but `hashCode()` remains inconsistent:

```
e1.equals(e2) = true

but

e1.hashCode() != e2.hashCode()
```

the two logical keys may end up treated as separate `HashMap` keys.

### What If Only hashCode() Is Overridden?

The PDF shows:

```
same hashCode
but
Object.equals() = false
```

so both objects remain distinct keys.

This is legal because:

```
same hash
does NOT imply equal objects
```

### Both Correct?

When both methods follow the contract, logically equal keys are treated consistently and the previous value can be replaced.

## Question 23: Why should HashMap keys preferably be immutable?

**Priority:** 🔥🔥 Must Know | ⚠️ Tricky

Suppose:

```java
class UserKey {

    String username;

    @Override
    public int hashCode() {
        return username.hashCode();
    }
}
```

Then:

```java
UserKey key = new UserKey("abhilash");

map.put(key, value);
```

Later:

```java
key.username = "rahul";
```

Now:

```
old username
→ hash H1
→ stored according to H1

new username
→ hash H2
→ lookup based on H2
```

The entry can become difficult/impossible to retrieve using the mutated key as expected.

Therefore:

Fields participating in key equality and hashing should remain stable while the key is in the map.

This is one reason:

```
String
```

is such a good Map key.

## Question 25: What is ConcurrentHashMap?

**Priority:** 🔥🔥 Must Know | 🔄 Modernization
**Source:** 📘 PDF Question 107

### Short Interview Answer

`ConcurrentHashMap` is a thread-safe concurrent `Map` implementation designed to permit significantly more concurrency than synchronizing an entire ordinary `HashMap`. Reads generally do not require locking the whole map, and updates coordinate at a much finer granularity.

The PDF correctly emphasizes better concurrency compared with locking the entire map and notes that null keys/values are not supported.

### ⚠️ Major Modern Correction

The PDF says:

```
ConcurrentHashMap
→ divided into 16 segments
→ writes lock a segment
```

That describes the older pre-Java-8 architecture.

Do not give this as the current implementation answer.

For modern Java interview preparation:

Java 8+ `ConcurrentHashMap` removed the old fixed `Segment[]` design. It uses a table-based structure with finer-grained coordination, CAS-style operations in some paths, and synchronization at individual bin/node level when needed rather than locking one of 16 permanent segments.

### Interview Trap

**Interviewer:** How many segments does modern ConcurrentHashMap have?

Bad answer:

```
16
```

Better:

The fixed segment architecture belongs to the older implementation. Modern `ConcurrentHashMap` no longer uses that design.

🔥 This is exactly the kind of answer that distinguishes outdated memorization from understanding.

### Why Doesn't ConcurrentHashMap Allow null?

**Priority:** 🔥 Tricky

Consider:

```java
map.get(key)
```

returns:

```
null
```

In a concurrent environment, should that mean:

```
key isn't present
```

or:

```
key is present and mapped to null
```

Avoiding null removes that ambiguity and simplifies concurrent semantics.

## Question 26: HashMap vs Hashtable vs ConcurrentHashMap

**Priority:** 🔥🔥 Must Know
**Source:** ➕ Added; HashTable is required by your master syllabus

| Feature | HashMap | Hashtable | ConcurrentHashMap |
|---|---|---|---|
| Thread-safe | ❌ | ✅ | ✅ |
| General synchronization model | none | coarse synchronized methods | fine-grained concurrent design |
| Null key | ✅ one | ❌ | ❌ |
| Null values | ✅ | ❌ | ❌ |
| Modern recommendation | ordinary non-concurrent map | legacy | concurrent map |

### Short Interview Answer

`HashMap` is the normal choice when external synchronization isn't required. `Hashtable` is a legacy synchronized `Map` implementation. `ConcurrentHashMap` is generally preferred for highly concurrent shared-map use because it allows much greater concurrency than locking the entire map.

## Question 27: What is HashSet?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 108

### Short Interview Answer

`HashSet` implements `Set` and stores unique elements using hashing. Internally, it is backed by a `HashMap`: the Set element is stored as the Map key and a shared dummy object is used as the value.

The PDF shows this explicitly:

```java
private transient HashMap<E,Object> map;

private static final Object PRESENT =
        new Object();
```

and:

```java
public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}
```

### Why Does HashSet Not Allow Duplicates?

Suppose:

```java
set.add("Java");
set.add("Java");
```

Internally, conceptually:

```java
map.put("Java", PRESENT);
map.put("Java", PRESENT);
```

Since HashMap keys are unique:

```
same key
    ↓
same mapping
```

so the Set contains one logical element.

### contains()

The PDF shows:

```java
set.contains(object)
```

ultimately delegating conceptually to:

```java
map.containsKey(object)
```

Therefore `HashSet` also depends heavily on:

```
equals()
+
hashCode()
```

## Question 29: What is LinkedHashMap?

**Priority:** 🔥 Important
**Source:** ➕ Missing dedicated PDF question

### Short Interview Answer

`LinkedHashMap` is a `HashMap` variant that also maintains a linked ordering of entries. By default it preserves insertion order, and it can also be configured for access order, which is useful for structures such as LRU-style caches.

Example:

```java
Map<Integer, String> map =
        new LinkedHashMap<>();

map.put(3, "C");
map.put(1, "A");
map.put(2, "B");
```

Iteration preserves:

```
3
1
2
```

in insertion order.

Compare:

```
HashMap
→ no insertion-order guarantee

LinkedHashMap
→ insertion order

TreeMap
→ sorted key order
```

## Question 30: What is TreeMap?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 109

The PDF describes `TreeMap` as a sorted `Map` backed by a Red-Black tree, using natural key ordering or a provided `Comparator`, with basic operations around O(log n).

### Short Interview Answer

`TreeMap` is a sorted `NavigableMap` implementation based on a Red-Black tree. Keys are ordered either according to their natural ordering or according to a `Comparator` supplied when the map is constructed. Basic lookup, insertion, and removal operations are typically O(log n).

Example:

```java
Map<Integer, String> map =
        new TreeMap<>();

map.put(30, "C");
map.put(10, "A");
map.put(20, "B");
```

Iteration:

```
10=A
20=B
30=C
```

### Natural Ordering

If keys are:

```
Integer
String
```

they already implement:

```
Comparable
```

The PDF demonstrates that Integer keys naturally sort ascending.

### Custom Ordering

```java
TreeMap<Employee, String> map =
        new TreeMap<>(
            Comparator.comparing(Employee::getAge)
        );
```

Now ordering comes from the `Comparator`.

## Question 31: How does TreeMap determine whether keys are equal?

**Priority:** ⚠️ Tricky | 🧠 Deep Understanding

This surprises many freshers.

`TreeMap` relies on:

```

```

That is:

```

```


If the comparison says:


`TreeMap` treats keys as occupying the same ordering position.

This is why your comparison logic must be designed carefully.

## Question 34: What is an Iterator?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Questions 111–113

### Short Interview Answer

`Iterator` provides a standard mechanism to traverse collection elements sequentially without exposing the underlying data structure. Common methods are `hasNext()`, `next()`, and `remove()`.

Example:

```java
Iterator<String> iterator =
        names.iterator();

while (iterator.hasNext()) {

    String value = iterator.next();

    System.out.println(value);
}
```

### Why Not Always Use Indexes?

A `Set` doesn't naturally have:

```java
set.get(0);
```

An iterator gives a common traversal mechanism:

```
ArrayList
HashSet
TreeSet
...
   ↓
Iterator
```

## Question 35: What is fail-fast iteration?

**Priority:** 🔥🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF Question 111

The PDF explains that collections such as `ArrayList` maintain structural modification information such as `modCount`, while an iterator tracks an expected value. If they differ during iterator operations, `ConcurrentModificationException` can be thrown.

Example:

```java
List<String> list =
        new ArrayList<>();

list.add("A");
list.add("B");

for (String value : list) {

    list.remove(value);
}
```

This can produce:

```
ConcurrentModificationException
```

### Mental Model

When iterator is created:

```
expectedModCount = modCount
```

Collection modified structurally:

```
modCount changes
```

Iterator later checks:

```
expectedModCount != modCount
```

then:

```
ConcurrentModificationException
```

## Question 36: Why doesn't Iterator.remove() cause the same problem?

**Priority:** 🔥 Important
**Source:** 📘 PDF Question 113

The PDF notes that iterator-controlled removal is supported while direct collection removal during iteration can trigger concurrent-modification detection.

Correct:

```java
Iterator<String> iterator =
        list.iterator();

while (iterator.hasNext()) {

    String value = iterator.next();

    if (value.equals("A")) {
        iterator.remove();
    }
}
```

Why?

Because the iterator itself performs the modification and updates its own tracking consistently.

## Question 37: What is "fail-safe" iteration?

**Priority:** 🔥 Important | 🔄 Terminology Correction

The PDF uses the common interview term fail-safe and gives:

```
CopyOnWriteArrayList
ConcurrentHashMap
```

as examples.

But there is an important correction:

"Fail-safe" is common interview terminology, not a precise official Java Collections API category.

Also, not all concurrent iterators simply iterate over a cloned collection.

**CopyOnWriteArrayList**

Its iterator effectively works with a snapshot.

**ConcurrentHashMap**

Its iterators are better described as:

```
weakly consistent
```

They can tolerate concurrent updates without throwing `ConcurrentModificationException`, but they don't promise a frozen snapshot.

So don't say:

"ConcurrentHashMap iterator works on a clone."

That is too simplistic.

## Question 38: Iterator vs ListIterator

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 112

The PDF gives the important differences.

| Iterator | ListIterator |
|---|---|
| Forward traversal | Forward + backward |
| Works broadly with collections | Only Lists |
| remove() | remove() |
| Cannot add() | Can add() |
| No set() | Has set() |
| No index methods | nextIndex(), previousIndex() |

Example:

```java
ListIterator<String> iterator =
        list.listIterator();

    System.out.println(iterator.next());

while (iterator.hasPrevious()) {
    System.out.println(iterator.previous());
}
```

## Question 39: Comparable vs Comparator in Collections

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Questions 37–39, connected here

The PDF describes:

```
Comparable
→ compareTo()
→ natural/default ordering

Comparator
→ compare()
→ alternate/custom ordering
```

and notes `Comparator` doesn't require modifying the target class.

### Comparable

```java
class Employee
        implements Comparable<Employee> {

    @Override
    public int compareTo(Employee other) {
        return this.id - other.id;
    }
}
```

Represents the class's:

```
natural ordering
```

### Comparator

```java
Comparator<Employee> byName =
        Comparator.comparing(
                Employee::getName
        );
```

Another:

```java
Comparator<Employee> bySalary =
        Comparator.comparing(
                Employee::getSalary
        );
```

Multiple ordering strategies.

## Common Fresher Mistakes

**❌ "Map extends Collection."**

No.

**❌ "ArrayList is always faster than LinkedList."**

Wrong.

Performance depends on operation and access pattern.

**❌ "LinkedList insertion is always O(1)."**

Only link manipulation is O(1) once the node/location is known.

**❌ "HashMap get() is guaranteed O(1)."**

Better:

Expected/average O(1) under good hashing; collision patterns can affect it.

**❌ "Same hashCode means same key."**

No.

```
same hash
≠
equal
```

**❌ "HashMap only uses hashCode."**

No.

```
hash
+
key equality
```

both matter.

**❌ "HashSet has its own completely separate uniqueness algorithm."**

Internally it is backed by `HashMap` in the implementation discussed by the PDF.

**❌ "ConcurrentHashMap has 16 segments."**

Outdated.

**❌ "Hashtable is the best thread-safe map."**

Usually not for modern concurrent code.

**❌ "TreeMap uses hashCode."**

Its ordering/search is tree/comparison based.

**❌ "final List means immutable."**

No.

## Collections Interviewer Grill Round

**Interviewer**
What is the Collections Framework?

**Candidate**
It's Java's architecture of interfaces, implementations, and utility algorithms for storing and manipulating groups of objects.

**Interviewer**
Difference between Collection and Collections?

**Candidate**
`Collection` is an interface in the hierarchy, while `Collections` is a utility class containing static methods such as `sort()` and `unmodifiableList()`.

**Interviewer**
Is Map a Collection?

**Candidate**
No. `Map` is part of the Collections Framework but doesn't extend `Collection` because it represents key-value mappings rather than individual elements.

**Interviewer**
ArrayList vs array?

**Candidate**
An array has fixed length after creation, while `ArrayList` manages a resizable backing array and provides List operations such as add, remove and contains.

**Interviewer**
What does ArrayList use internally?

**Candidate**
A dynamically managed array of element references, represented by an `Object[]`-style backing array in its implementation.

**Interviewer**
What is the default ArrayList capacity?

**Candidate**
Ten is the commonly discussed default capacity, but a default-constructed modern `ArrayList` initially uses an empty backing array and allocates capacity on the first insertion.

**Interviewer**
How does ArrayList grow?

**Candidate**
When its backing array can't hold another element, it allocates larger storage and copies the existing references. The implementation discussed here grows by roughly 50%, though exact implementation details shouldn't be treated as language guarantees.

**Interviewer**
Complexity of adding to ArrayList?

**Candidate**
Appending is amortized O(1), but a resize is O(n). Insertion at an arbitrary middle index is O(n) because elements must shift.

**Interviewer**
Why is LinkedList get O(n)?

**Candidate**
Because elements are stored as linked nodes rather than direct array indexes, so reaching an arbitrary index requires traversal.

**Interviewer**
Then LinkedList insertion is always O(1), right?

**Candidate**
The link update itself can be O(1), but finding an arbitrary indexed position can still be O(n).

**Interviewer**
Explain HashMap internally.

**Candidate**
`HashMap` uses a table of buckets. It processes the key's hash to identify a bucket, then examines entries in that bucket and uses equality to identify the logical key.

**Interviewer**
Why do we need equals if hashCode already gives us the bucket?

**Candidate**
Because different keys can map to the same bucket or hash. Hashing narrows the search; equality determines whether a candidate is actually the same logical key.

**Interviewer**
What is a collision?

**Candidate**
When different keys map to the same bucket.

**Interviewer**
Does that mean hashCode is badly implemented?

**Candidate**
Not necessarily. Collisions are normal and unavoidable. A poor hash distribution simply causes too many of them and hurts performance.

**Interviewer**
What happens after many collisions?

**Candidate**
Entries initially use a linked bucket structure, and in Java 8+ sufficiently large collided bins may become tree-based when the treeification conditions are met, improving worst-case lookup within that bin.

**Interviewer**
Why must equals and hashCode agree?

**Candidate**
If two keys are logically equal, they must have the same hash code so hash-based collections search them consistently.

**Interviewer**
Why are mutable HashMap keys dangerous?

**Candidate**
If fields used by equality or hashing change after insertion, the key's hash/equality behavior can change while its entry remains stored according to the previous state.

**Interviewer**
How does HashSet maintain uniqueness?

**Candidate**
`HashSet` is backed by `HashMap`. The Set element becomes a HashMap key and a dummy object acts as the value, so HashMap's unique-key behavior enforces Set uniqueness.

**Interviewer**
HashSet vs TreeSet?

**Candidate**
`HashSet` uses hashing and doesn't guarantee sorted order. `TreeSet` is tree-based, maintains sorted elements, and basic operations are O(log n).

**Interviewer**
HashMap vs TreeMap?

**Candidate**
`HashMap` is optimized for expected constant-time key lookup without sorted order. `TreeMap` maintains keys in sorted order using a Red-Black tree and provides O(log n) operations.

**Interviewer**
What about LinkedHashMap?

**Candidate**
It's hash-based but also maintains a linked ordering of entries, normally insertion order, and optionally access order.

**Interviewer**
ConcurrentHashMap uses 16 segments, correct?

**Candidate**
That's the older implementation. Modern Java 8+ `ConcurrentHashMap` no longer uses the fixed Segment array design; it uses finer-grained table/bin coordination and concurrent techniques such as CAS where appropriate.

**Interviewer**
What's fail-fast?

**Candidate**
A fail-fast iterator detects incompatible structural modification after iterator creation, typically through modification counters, and may throw `ConcurrentModificationException`.

**Interviewer**
Why can Iterator.remove() work safely?

**Candidate**
Because the iterator itself performs the structural modification and keeps its expected modification state consistent.

**Interviewer**
Is ConcurrentHashMap iterator "fail-safe"?

**Candidate**
That's common interview terminology, but more precisely `ConcurrentHashMap` iterators are weakly consistent: they tolerate concurrent updates and don't throw `ConcurrentModificationException`, but they don't provide a frozen snapshot.
