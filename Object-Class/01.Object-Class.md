## Question 1: What is the Object class in Java?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 40

**Difficulty:** Beginner
**Interview Frequency:** Very High

### What the Interviewer Is Testing

Whether you understand Java's class hierarchy and why methods like `equals()`, `hashCode()`, and `toString()` are available on almost every object.

### Short Interview Answer

`java.lang.Object` is the root superclass of Java's ordinary class hierarchy. If a class doesn't explicitly extend another class, it implicitly extends `Object`. Because of that, every class ultimately inherits `Object`'s common behavior such as `equals()`, `hashCode()`, `toString()`, and `getClass()`.

The PDF describes `Object` as sitting at the top of the hierarchy.

### Root-Level Understanding

Suppose you write:

```java
class Employee {
}
```

You didn't write:

```java
class Employee extends Object {
}
```

but conceptually Java treats the hierarchy as:

```
Object
   ↑
Employee
```

Now suppose:

```java
class Person {
}

class Employee extends Person {
}
```

The hierarchy becomes:

```
Object
   ↑
Person
   ↑
Employee
```

This is important.

`Employee` does not directly extend both `Person` and `Object`.

It has only one direct superclass:

```
Employee → Person
```

and `Person` ultimately inherits from:

```
Object
```

So Java's single-inheritance rule is not violated.

## Question 3: What is equals()?

**Priority:** 🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF + interviewer expansion

### Short Interview Answer

`equals()` is used to define logical equality between objects. The default implementation inherited from `Object` effectively provides identity-based equality, so two different objects are not equal merely because their fields contain the same values. Classes such as `String` override `equals()` to compare meaningful contents instead.

The PDF makes this distinction when explaining `String`: `Object`'s `equals()` compares object identity/reference behavior, whereas `String` overrides it to compare content.

### Why Do We Need equals()?

Suppose:

```java
class Employee {

    int id;
    String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }
}
```

Now:

```java
Employee e1 = new Employee(101, "Abhilash");
Employee e2 = new Employee(101, "Abhilash");
```

Logically:

```
e1:
id   = 101
name = Abhilash

e2:
id   = 101
name = Abhilash
```

We might consider them the same employee.

But:

```java
System.out.println(e1 == e2);
```

returns:

```
false
```

because they are two different objects.

And without overriding `equals()`:

```java
System.out.println(e1.equals(e2));
```

also returns `false`.

## Question 4: What is the difference between == and equals()?

**Priority:** 🔥 Must Know | ⚠️ Very Common Trap

### Short Interview Answer

For primitive values, `==` compares the primitive values. For object references, `==` checks whether the two references point to the same object. `equals()` is a method used for logical equality, and its behavior depends on whether the class overrides it.

### Primitive

```java
int a = 10;
int b = 10;

System.out.println(a == b);
```

Output:

```
true
```

The values are compared.

### Objects

```java
Employee e1 = new Employee(1, "A");
Employee e2 = new Employee(1, "A");

System.out.println(e1 == e2);
```

Output:

```
false
```

Conceptually:

```
e1 ─────► Employee object #1

e2 ─────► Employee object #2
```

Different objects.

### Same Reference

```java
Employee e1 = new Employee(1, "A");
Employee e2 = e1;

System.out.println(e1 == e2);
```

Output:

```
true
```

Because:

```
e1 ──┐
     ├────► same Employee
e2 ──┘
```

## Question 5: Why should we override equals()?

**Priority:** 🔥 Must Know | 🧠 Deep Understanding

### The Root Problem

Imagine:

```java
Employee e1 = new Employee(101, "Abhilash");
Employee e2 = new Employee(101, "Abhilash");
```

Business requirement:

Employees having the same employee ID should be considered the same employee.

Java cannot know that.

Java doesn't know whether equality means:

- same ID?
- same email?
- same username?
- all fields?

That is domain-specific.

So we define it.

### Example

```java
class Employee {

    private int id;
    private String name;

    Employee(int id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) {
            return true;
        }

        if (obj == null) {
            return false;
        }

        if (getClass() != obj.getClass()) {
            return false;
        }

        Employee other = (Employee) obj;

        return id == other.id;
    }
}
```

Now:

```java
Employee e1 = new Employee(101, "Abhilash");
Employee e2 = new Employee(101, "Abhilash");

System.out.println(e1.equals(e2));
```

returns:

```
true
```

because we've defined:

```
same employee ID
        ↓
logically equal employees
```

## Question 6: What is the equals() contract?

**Priority:** 🔥 Must Know | 🧠 Deep Understanding
**Source:** ➕ Interviewer expansion around PDF's equality discussion

A good `equals()` implementation should satisfy several properties.

### 1. Reflexive

For any non-null `x`:

```
x.equals(x)
```

must be:

```
true
```

### 2. Symmetric

If:

```
x.equals(y)
```

is true, then:

```
y.equals(x)
```

must also be true.

### 3. Transitive

If:

```
x equals y
y equals z
```

then:

```
x must equal z
```

### 4. Consistent

If nothing relevant changes:

```
x.equals(y)
```

should repeatedly return the same result.

### 5. Non-nullity

For non-null `x`:

```
x.equals(null)
```

must return:

```
false
```

## Question 7: What is hashCode()?

**Priority:** 🔥 Must Know

### Short Interview Answer

`hashCode()` returns an integer hash value for an object. Hash-based collections such as `HashMap` and `HashSet` use it to help determine where an object should be stored or searched. It does not uniquely identify an object because different objects can have the same hash code.

The PDF lists `hashCode()` as one of `Object`'s methods.

### Important Mental Model

Do not think:

```
hashCode = memory address
```

Do not think:

```
hashCode = unique ID
```

Think:

```
object
   |
   | hashCode()
   v
integer hash
   |
   v
helps hash-based collection
find a bucket/location
```

Different objects can produce the same hash code.

That's called a hash collision.

## Question 8: What is the equals() and hashCode() contract?

**Priority:** 🔥🔥 Must Know | ⚠️ Extremely Important
**Source:** 📘 PDF Question 34

The PDF states the central contract:

If two objects are equal according to `equals()`, their hash codes must be the same; the reverse is not necessarily true.

### Short Interview Answer

If two objects are equal according to `equals()`, they must return the same hash code. However, two objects having the same hash code are not necessarily equal because hash collisions are allowed.

Mathematically:

```
equals() == true
        ↓
same hashCode()
```

But:

```
same hashCode()
        ↓
may or may not be equal
```

### Why Doesn't Same Hash Code Mean Equal?

Because `hashCode()` returns an `int`.

There is a limited range of possible integer values.

But Java programs can create far more possible object states.

Therefore collisions are unavoidable in principle.

Example:

```
Employee A ──► hash = 42
Employee B ──► hash = 42
```

That does not prove:

```
Employee A == Employee B logically
```

So hash-based collections may still need `equals()` to resolve candidates.

## Question 9: Why must we override hashCode() when we override equals()?

**Priority:** 🔥🔥 Must Know | ⚠️ Classic Interview Question

This is one of the most important questions in the entire Core Java interview.

### Short Interview Answer

Because hash-based collections use both methods. `hashCode()` helps locate the bucket, while `equals()` determines whether a matching logical key exists within the candidate entries. If two objects are equal according to `equals()` but return different hash codes, they can end up being searched in different buckets, causing collections such as `HashMap` and `HashSet` to behave incorrectly relative to our equality definition.

### Root Cause — Start Without HashMap

Suppose:

```java
Employee e1 = new Employee(101, "Abhilash");
Employee e2 = new Employee(101, "Abhilash");
```

We override:

```
equals()
```

such that:

```
e1.equals(e2) = true
```

But suppose we don't override:

```
hashCode()
```

Then they may produce:

```
e1.hashCode() = 1234
e2.hashCode() = 9876
```

Now the contract is broken:

```
equals = true

but

hash codes differ
```

The PDF explicitly examines exactly this scenario in its HashMap section: when only `equals()` is overridden but `Object`'s `hashCode()` is still used, logically equal custom keys can still be inserted separately.

## Question 10: How do equals() and hashCode() work inside HashMap?

**Priority:** 🔥🔥 Must Know | 🧠 Deep Understanding

We'll cover full HashMap internals in the Collections module.

For now, understand this simplified flow.

### put(key, value)

Suppose:

```java
map.put(employee, "Backend Developer");
```

Conceptually:

```
employee
   |
   v
hashCode()
   |
   v
hash processing
   |
   v
bucket/index
   |
   v
candidate entries
   |
   v
equals()
```

Very simplified logic:

```
1. Compute key's hash
2. Locate bucket
3. Examine candidate keys
4. Use equality checking
5. If logically same key → replace/update value
6. Otherwise → insert another entry
```

### get(key)

```java
map.get(employee);
```

Conceptually:

```
key.hashCode()
      ↓
find candidate bucket
      ↓
compare candidate keys
      ↓
equals()
      ↓
return matching value
```

This is why both methods matter.

## Question 11: What happens when neither equals() nor hashCode() is overridden?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF HashMap scenario 1

The PDF specifically tests this using custom Employee keys.

When a custom class overrides neither method, `Object`'s implementations apply, so separately created objects are considered different even when their fields contain equivalent values.

The PDF's example shows two separately created employee objects being inserted independently, while two variables referencing the exact same object behave as the same key.

### Mental Model

```java
Employee e1 = new Employee(1, "A");
Employee e2 = new Employee(1, "A");
```

Without overrides:

```
e1.equals(e2) → false
```

So:

```java
map.put(e1, 100);
map.put(e2, 200);
```

can represent two distinct keys.

## Question 12: What happens if only equals() is overridden?

**Priority:** 🔥 Must Know | ⚠️ Tricky

Suppose:

```
e1.equals(e2) = true
```

but:

```
e1.hashCode() != e2.hashCode()
```

Now equal objects can be routed through different hash locations.

This violates the contract.

The PDF explicitly describes this situation and shows that both custom Employee objects still get inserted.

### Interview Answer

This is incorrect because equal objects must have equal hash codes. Hash-based collections may fail to treat them as the same logical key.

## Question 13: What happens if only hashCode() is overridden?

**Priority:** 🔥 Must Know | ⚠️ Tricky

Suppose:

```
e1.hashCode() = 10
e2.hashCode() = 10
```

but `equals()` remains `Object`'s identity-style implementation.

Then:

```
same hashCode
```

doesn't mean:

```
equal
```

The PDF tests this as Scenario 3: the objects share a hash code, but `Object`'s `equals()` still sees separate references, so both are treated as distinct keys.

This doesn't necessarily violate the equals/hashCode contract.

Remember:

```
same hashCode
        ↓
does NOT require equals == true
```

Collisions are valid.

## Question 14: What happens when both are implemented correctly?

**Priority:** 🔥 Must Know

Suppose:

```
e1.equals(e2) == true
```

and:

```
e1.hashCode() == e2.hashCode()
```

Then hash-based collections can correctly recognize them as the same logical key.

The PDF's Scenario 4 shows the existing map value being replaced when both equality and hash code are implemented consistently.

### The Four Scenarios — Must Memorize the Reasoning

| equals() | hashCode() | Result |
|---|---|---|
| ❌ default | ❌ default | identity semantics |
| ✅ custom | ❌ default | ❌ contract can break |
| ❌ default | ✅ custom | hash collisions possible; identity still controls equality |
| ✅ custom | ✅ consistent | ✅ correct logical-key behavior |

Do not memorize only this table.

Understand:

```
hashCode
    ↓
narrows search

equals
    ↓
confirms logical equality
```

## Question 15: Show a correct equals() + hashCode() implementation

**Priority:** 🔥 Must Know | 💻 Coding

Modern Java code usually uses:

```
Objects.equals(...)
Objects.hash(...)
```

Example:

```java
import java.util.Objects;

class Employee {

    private final int id;
    private final String email;

    Employee(int id, String email) {
        this.id = id;
        this.email = email;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) {
            return true;
        }

        if (obj == null || getClass() != obj.getClass()) {
            return false;
        }

        Employee other = (Employee) obj;

        return id == other.id
                && Objects.equals(email, other.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, email);
    }
}
```

Notice something very important:

```
equals uses:
id + email

hashCode uses:
id + email
```

The same equality-significant state should normally drive both.

## Question 16: Why is using a mutable object as a HashMap key dangerous?

**Priority:** 🔥 Must Know | 🧠 Deep Understanding | ⚠️ Tricky

This is an excellent follow-up.

Imagine:

```java
class Employee {

    int id;

    @Override
    public int hashCode() {
        return Integer.hashCode(id);
    }

    @Override
    public boolean equals(Object o) {
        ...
    }
}
```

Now:

```java
Employee e = new Employee();
e.id = 100;

map.put(e, "Developer");
```

At insertion:

```
id = 100
hashCode = H1
bucket = B1
```

Then:

```java
e.id = 500;
```

Now:

```
id = 500
hashCode = H2
bucket expected = B2
```

But the entry physically remains where it was stored according to the earlier hash.

Then:

```java
map.get(e)
```

may search using the new hash-derived location and fail to find the entry as expected.

### Interview Answer

HashMap keys should ideally be immutable with respect to the fields used by `equals()` and `hashCode()`. If those fields change after insertion, the key's logical hash location can change while the entry remains stored using the previous state.

This is one reason immutable objects are excellent map keys.

We'll connect this with `String` in the next module.

## Question 17: What is toString()?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Object-method list

The PDF describes `toString()` as returning a string representation of an object.

### Short Interview Answer

`toString()` returns a textual representation of an object. `Object` provides a default implementation, but we normally override it when a meaningful representation helps with logging, debugging, and diagnostics.

### Without Override

```java
Employee employee = new Employee();

System.out.println(employee);
```

You may see something conceptually similar to:

```
Employee@6d311334
```

That is usually not useful to a developer.

### Override It

```java
@Override
public String toString() {
    return "Employee{id=" + id +
           ", name='" + name + "'}";
}
```

Now:

```java
System.out.println(employee);
```

might print:

```
Employee{id=101, name='Abhilash'}
```

### Why Does println(object) Use toString()?

Because printing an object ultimately needs a string representation.

This becomes useful for:

- logging
- debugging
- exceptions
- development diagnostics

### Real-World Backend Warning

Do not blindly include:

- password
- JWT
- API key
- access token
- credit-card data

inside `toString()`.

For example, this is dangerous:

```java
@Override
public String toString() {
    return "User{email=" + email +
            ", password=" + password + "}";
}
```

because logs may expose sensitive information.

## Question 19: What is clone()?

**Priority:** ⭐ Important | ⚠️ Tricky
**Source:** 📘 PDF Questions 40 and 54

The PDF describes `Object.clone()` as creating a copy and explains that a class implements `Cloneable` to indicate that cloning through `Object.clone()` is permitted. Otherwise `CloneNotSupportedException` is thrown.

### Short Interview Answer

`clone()` is a protected method inherited from `Object` that can create a field-by-field copy of an object. For the standard `Object.clone()` mechanism, the class generally implements the marker interface `Cloneable`; otherwise cloning throws `CloneNotSupportedException`.

### Reference Copy vs Cloning

This:

```java
Employee e1 = new Employee();
Employee e2 = e1;
```

does not copy an object.

Conceptually:

```
e1 ──┐
     ├────► same Employee
e2 ──┘
```

The PDF demonstrates this: assigning `e2 = e1` results in both references pointing to the same employee, so changing through one reference is visible through the other.

Cloning instead creates another top-level object:

```
e1 ─────► Employee #1

e2 ─────► Employee #2
```

But now we hit another important problem.

## Question 20: What is a shallow copy?

**Priority:** 🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF Question 55

The PDF explains that `Object`'s default cloning is shallow: primitive/simple field values are copied, while referenced nested objects remain shared by reference.

Suppose:

```java
class Company {
    String name;
}

class Employee {
    int id;
    Company company;
}
```

Original:

```
Employee e1
   |
   +-- id = 1
   |
   +-- company ─────► Company A
```

After shallow copy:

```
Employee e1                   Employee e2
   |                              |
   +-- id = 1                     +-- id = 1
   |                              |
   +-- company ────┐      ┌────── +-- company
                   │      │
                   ▼      ▼
                  Company A
```

Both objects share:

```
same Company instance
```

So:

```java
e2.company.name = "New Company";
```

can also appear through:

```java
e1.company.name
```

The PDF explicitly explains that in shallow copying the referenced `Company` remains shared, so modifications are reflected through both copies.

## Question 21: What is a deep copy?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF

### Short Interview Answer

In a deep copy, mutable nested objects are also copied so that the copied object does not share those mutable components with the original.

The PDF defines deep copy as also cloning non-primitive/reference members to make original and copy independent.

Conceptually:

```
Original Employee
      |
      v
 Company A


Copied Employee
      |
      v
 Company B
```

Now:

```
Company A != Company B
```

They have independent mutable state.

### Shallow vs Deep Copy

| Shallow Copy | Deep Copy |
|---|---|
| Top-level object copied | Top-level object copied |
| Nested references may be shared | Mutable nested objects copied too |
| Faster/simpler | More work |
| Changes to shared nested objects may affect both | Copies can be independent |

The PDF also shows a copy constructor as an alternative approach for deep copying.

## Question 22: Clone vs Copy Constructor — which is easier to reason about?

**Priority:** ⭐ Important
**Source:** 📘 PDF mentions copy constructor + ➕ interviewer expansion

Example:

```java
class Employee {

    private String name;
    private Company company;

    Employee(Employee other) {
        this.name = other.name;
        this.company =
                new Company(other.company.getName());
    }
}
```

Usage:

```java
Employee e2 = new Employee(e1);
```

A copy constructor lets us explicitly decide:

- which fields should be copied?
- which mutable objects need new instances?
- which immutable values can safely be reused?

That often makes copying semantics clearer.

## Question 23: What is finalize()?

**Priority:** ⚠️ Tricky / Historical
**Source:** 📘 PDF + 🔄 Modern Java note

The PDF lists:

```java
protected void finalize() throws Throwable
```

and describes it as being called in connection with garbage collection when an object becomes unreachable.

### PDF-Level Interview Answer

Historically, `finalize()` was intended as a hook that could be invoked before an object's storage was reclaimed.

### 🔄 Modern Java Interview Expansion

For a current interview, do not stop there.

A much stronger answer is:

`finalize()` is a legacy cleanup mechanism and should not be relied on. Its execution timing was never deterministic, and modern Java has deprecated finalization for removal. Resources such as files, sockets, or database-related resources should be managed explicitly, normally through `AutoCloseable` and try-with-resources.

### Why Was finalize() Problematic?

Imagine:

```java
FileInputStream input = ...
```

You should not think:

```
I'll just wait for GC
      ↓
finalize()
      ↓
file gets closed
```

Why?

You don't control exactly when GC occurs.

For external resources, deterministic cleanup matters.

Better:

```java
try (FileInputStream input =
         new FileInputStream("data.txt")) {

    // use input
}
```

Now resource cleanup has a defined lifecycle.

## Real-World Example — Entity Equality

Suppose a backend has:

```java
class User {

    private Long id;
    private String email;
}
```

The question:

What makes two users logically equal?

could be based on:

- database ID?
- email?
- username?

That's not something Java can guess.

The developer must choose equality semantics carefully.

And once equality is defined, collections such as:

```
HashSet<User>
HashMap<User, ...>
```

depend heavily on that choice.

This is why `equals()` and `hashCode()` are not just "two Object methods."

They are a data-structure correctness contract.

## Common Fresher Mistakes

**❌ 1. "== compares values and equals() compares contents."**

Too generic and therefore dangerous.

Correct:

```
primitive ==
→ primitive value

reference ==
→ object identity/reference equality

equals()
→ behavior defined by that class
```

**❌ 2. "Same hashCode means objects are equal."**

Wrong.

```
equals → same hash

same hash ⇏ equals
```

**❌ 3. "hashCode is the memory address."**

Do not say this.

Treat it as an integer hash value used according to the hash-code contract.

**❌ 4. "I only need to override equals."**

Wrong for objects participating in hash-based collections.

If logical equality changes, `hashCode()` must remain consistent with that equality.

**❌ 5. "HashMap only uses hashCode."**

Wrong.

Conceptually:

```
hashing
   ↓
locate candidates

equality
   ↓
identify matching key
```

**❌ 6. "e2 = e1 creates a copy."**

No.

It copies the reference value.

**❌ 7. "clone() automatically performs a deep copy."**

No.

The PDF explicitly teaches that `Object`'s default cloning behavior is shallow.

**❌ 8. "GC guarantees finalize() will immediately execute."**

Do not rely on that assumption.

Modern Java treats finalization as legacy.

## Interviewer Grill Round — Object Class

Now the questions progressively become harder.

**Interviewer**
What is the parent class of every Java class?

**Candidate**
Ultimately `java.lang.Object`. If a class doesn't explicitly extend another class, it directly extends `Object`; otherwise `Object` is still normally somewhere at the top of its superclass chain.

**Interviewer**
Then if Employee extends Person, isn't Employee extending both Person and Object?

**Candidate**
No. Employee has only one direct superclass: Person. Person ultimately inherits from Object, so Employee inherits Object behavior indirectly. That doesn't violate Java's single class inheritance.

**Interviewer**
What important methods does Object provide?

**Candidate**
Important ones include `equals()`, `hashCode()`, `toString()`, `getClass()`, `clone()`, plus monitor methods `wait()`, `notify()` and `notifyAll()`. Historically there is also `finalize()`, which is now legacy/deprecated.

**Interviewer**
Difference between == and equals()?

**Candidate**
For references, `==` checks whether both references denote the same object. `equals()` checks logical equality according to the implementation provided by the class.

**Interviewer**
Does Object's default equals() compare employee fields?

**Candidate**
No. Unless the class overrides it, separate objects won't become logically equal merely because their fields contain the same values.

**Interviewer**
Then why override equals()?

**Candidate**
To define domain-specific logical equality, such as considering two employees equal when they have the same identity field.

**Interviewer**
Why should you override hashCode() as well?

**Candidate**
Because equal objects are required to produce the same hash code. Hash-based collections use hash information to locate candidate entries and equality to determine whether a matching logical key exists.

**Interviewer**
What if two objects have the same hash code?

**Candidate**
They may still be unequal. That's a valid hash collision.

**Interviewer**
What if two objects are equal but their hash codes are different?

**Candidate**
That's a violation of the equals/hashCode contract and can cause incorrect behavior in hash-based collections.

**Interviewer**
Suppose:
```java
e1.equals(e2) == true
```
but you didn't override hashCode(). What could happen in HashMap?

**Candidate**
They may produce different hash codes and therefore be searched in different hash locations, so HashMap may fail to treat them as the same logical key.

**Interviewer**
Suppose two objects have:
```
same hashCode
equals = false
```
Is that illegal?

**Candidate**
No. Hash collisions are allowed.

**Interviewer**
Can I use a mutable object as a HashMap key?

**Candidate**
Technically yes, but it's dangerous if fields participating in `equals()` or `hashCode()` change after insertion, because the key's hash/equality characteristics change while the entry remains stored according to the old state.

**Interviewer**
Why is String commonly considered a good HashMap key?

**Candidate**
One important reason is immutability. Once a String is created, its equality-significant value doesn't change, so its hash behavior remains stable while being used as a key.

We'll expand the full reasons in the String module.

**Interviewer**
What is shallow cloning?

**Candidate**
The top-level object is copied, but referenced mutable objects are still shared between original and clone.

**Interviewer**
What is deep copying?

**Candidate**
Nested mutable state is also copied so the new object can be independent of the original.

**Interviewer**
Does clone() call a normal constructor to create the clone?

**Candidate**
The standard Object cloning mechanism isn't equivalent to simply invoking our normal constructor. That's another reason copying through explicit constructors or factory methods can sometimes be easier to reason about.

**Interviewer**
Would you use finalize() for closing database connections?

**Candidate**
No. Resource cleanup should be explicit and deterministic, normally using the resource-management API such as `AutoCloseable` and try-with-resources. Finalization is legacy and shouldn't be relied on.
