## Question 1: What is an exception?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 14

**Difficulty:** Beginner
**Interview Frequency:** Very High

### Short Interview Answer

An exception represents an abnormal condition that occurs while a program is executing and interrupts its normal flow. Java represents exceptions as objects. Exception handling provides a structured way either to recover from the problem or propagate it to code that can handle it appropriately.

The PDF defines an exception as an event that disrupts the normal program flow and describes exception handling as the mechanism used to maintain the program's flow.

### Root Cause — Why Do Exceptions Exist?

Imagine:

```java
int result = 10 / 0;

System.out.println("Completed");
```

The CPU/program cannot produce a valid integer result for:

```
10 / 0
```

Something abnormal happened.

Without a structured mechanism, every method would need logic like:

```
did operation work?
did file exist?
did database connect?
did parsing succeed?
did API respond?
```

mixed into normal code.

Exceptions separate:

```
Normal execution
```

from:

```
Failure handling
```

### Example

```java
try {
    int result = 10 / 0;

    System.out.println(result);
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
}
```

Conceptually:

```
try
 |
 | operation
 v
exception occurs
 |
 v
matching catch?
 |
 +---- YES ----> catch executes
 |
 v
program continues afterward
```

## Question 2: What is exception handling?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 14

### Short Interview Answer

Exception handling is the mechanism Java provides to detect and respond to exceptional situations using constructs such as `try`, `catch`, `finally`, `throw`, `throws`, and try-with-resources. Depending on the situation, we can recover, translate the exception, clean resources, or propagate the failure to the caller.

### Important Engineering Point

Handling doesn't necessarily mean:

```java
catch (Exception e) {
    System.out.println("Error");
}
```

Sometimes the correct handling is:

```
Controller
   ↓
Service
   ↓
Repository
   ↓
Database exception
   ↓
Service translates exception
   ↓
Controller returns appropriate HTTP response
```

An exception should usually be handled at the level that actually knows what the failure means.

```
                     Object
                        |
                    Throwable
                   /         \
                  /           \
               Error        Exception
                               |
                      RuntimeException
```

A more useful view:

```
Throwable
├── Error
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── ...
│
└── Exception
    ├── IOException
    ├── SQLException
    ├── ClassNotFoundException
    │
    └── RuntimeException
        ├── NullPointerException
        ├── ArithmeticException
        ├── IllegalArgumentException
        ├── IndexOutOfBoundsException
        └── ...
```

### Why Throwable?

Java allows objects derived from:

```
Throwable
```

to participate in Java's throw/catch mechanism.

## Question 4: What is the difference between Error and Exception?

**Priority:** 🔥 Must Know | ⚠️ Often Oversimplified
**Source:** 📘 PDF Question 15

The PDF describes errors as severe problems such as `OutOfMemoryError` and `StackOverflowError`, while exceptions represent conditions the application may be able to handle.

### Better Interview Answer

Both `Error` and `Exception` extend `Throwable`. Exceptions generally represent problems application code may reasonably anticipate or handle. Errors normally represent serious JVM/runtime or environmental problems that ordinary application code is generally not expected to recover from, such as `OutOfMemoryError` or `StackOverflowError`.

### Important Clarification

Do not memorize:

"Errors can never be caught."

Technically:

```java
catch (Error e) {
}
```

can be written.

The important question is:

Should normal application code attempt to recover from Errors?

Usually, no.

### Examples

**Exception**

```java
Integer.parseInt("abc");
```

may produce:

```
NumberFormatException
```

The application might respond:

```
Invalid input
```

**Error**

```java
void recurse() {
    recurse();
}
```

may eventually produce:

```
StackOverflowError
```

That's generally a programming/runtime failure requiring correction rather than routine business recovery.

## Question 5: What are checked and unchecked exceptions?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 16

The PDF separates exceptions into checked exceptions, for which the compiler requires handling/declaration, and unchecked `RuntimeException` types, for which the compiler doesn't impose that requirement.

### Short Interview Answer

Checked exceptions are exception types that the compiler requires us either to catch or declare with `throws`. They are generally subclasses of `Exception` excluding `RuntimeException`. Unchecked exceptions are `RuntimeException` and its subclasses; the compiler doesn't force us to catch or declare them.

### Checked Exception

Example:

```java
FileInputStream input =
        new FileInputStream("data.txt");
```

The file:

```
might not exist
```

so Java may report:

```
FileNotFoundException
```

The compiler requires:

```
catch it
OR
declare it
```

Example:

```java
try {
    FileInputStream input =
            new FileInputStream("data.txt");
} catch (FileNotFoundException e) {
    // handle
}
```

or:

```java
void readFile() throws FileNotFoundException {
    FileInputStream input =
            new FileInputStream("data.txt");
}
```

### Unchecked Exception

Example:

```java
String name = null;

System.out.println(name.length());
```

Result:

```
NullPointerException
```

The compiler doesn't force:

```
try/catch
```

around it.

Why?

Because many runtime exceptions represent programming/precondition problems that should often be prevented rather than blindly caught everywhere.

### Checked vs Unchecked

| Checked | Unchecked |
|---|---|
| Compiler enforces catch/declare | Compiler doesn't enforce |
| Subclasses of Exception excluding RuntimeException | RuntimeException subclasses |
| IOException | NullPointerException |
| SQLException | IllegalArgumentException |
| ClassNotFoundException | ArithmeticException |

## Question 6: Why were checked exceptions introduced?

**Priority:** 🧠 Deep Understanding

Suppose a method performs an operation with an external failure possibility:

```
readFile()
```

The caller should know:

Reading may fail because the file is unavailable.

Checked exceptions can make that part of the method contract:

```java
void readFile() throws IOException
```

The compiler then forces callers to acknowledge it.

### But There Is a Trade-off

Checked exceptions can improve explicit failure handling.

But excessive checked exceptions can also cause:

```
throws A
throws B
throws C
catch everywhere
```

and create noisy APIs.

That's why experienced engineers choose exception types based on whether callers can reasonably recover.

## Question 7: How does try-catch work?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 17

The PDF says potentially exception-producing statements are placed in the `try` block, and a `try` must be associated with `catch`, `finally`, or both.

### Example

```java
try {
    int result = 10 / 0;

} catch (ArithmeticException e) {
    System.out.println("Invalid division");
}
```

Flow:

```
try begins
    ↓
statement 1
    ↓
exception thrown
    ↓
remaining statements in try skipped
    ↓
matching catch selected
    ↓
catch executes
    ↓
execution continues afterward
```

### Important Follow-Up

What happens here?

```java
try {
    System.out.println("A");

    int x = 10 / 0;

    System.out.println("B");

} catch (ArithmeticException e) {
    System.out.println("C");
}
```

Output:

```
A
C
```

Not:

```
A
B
C
```

Once the exception occurs, control leaves the remaining portion of the try.

## Question 9: What is finally?

**Priority:** 🔥🔥 Must Know

### Short Interview Answer

`finally` is used for code that should execute as control exits a try/catch structure, regardless of whether normal execution or an exception occurs in the usual cases. It has historically been used for cleanup, although resources implementing `AutoCloseable` should normally be handled with try-with-resources.

Example:

```java
try {
    System.out.println("Processing");

} catch (Exception e) {
    System.out.println("Failed");

} finally {
    System.out.println("Cleanup");
}
```

## Question 10: When might finally not execute?

**Priority:** 🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF Question 20

The PDF lists:

```
System.exit()
JVM crash
```

as examples where `finally` will not execute.

### Interview Answer

In normal Java control flow, `finally` is strongly expected to run. But it can't be guaranteed if the JVM terminates before reaching it, for example through `System.exit(...)`, a JVM/process crash, or abrupt external process termination.

So avoid saying:

"finally always executes."

Better:

"finally normally executes even when a return or exception occurs, unless execution of the JVM/process is terminated before it can run."

## Question 11: How do multiple catch blocks work?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 19

The PDF gives two approaches:

```
Multiple catch blocks
Multi-catch using |
```

and emphasizes catching more-specific exceptions before broader ones.

### Example

```java
try {

} catch (FileNotFoundException e) {

} catch (IOException e) {

} catch (Exception e) {

}
```

Correct order:

```
Specific
   ↓
More general
   ↓
Most general
```

### Why Does Catch Ordering Matter?

Consider:

```java
try {

} catch (Exception e) {

} catch (IOException e) {

}
```

This is invalid.

Why?

Because:

```
IOException IS-A Exception
```

so the first block already catches it.

The second block can never execute.

```
Exception
   ↑
IOException
   ↑
FileNotFoundException
```

Therefore:

```
FileNotFoundException
       ↓
IOException
       ↓
Exception
```

is valid ordering.

## Question 12: What is multi-catch?

**Priority:** ⭐ Important
**Source:** 📘 PDF Question 19

Instead of:

```java
catch (IOException e) {
    handle(e);
}

catch (SQLException e) {
    handle(e);
}
```

when handling logic is the same:

```java
catch (IOException | SQLException e) {
    handle(e);
}
```

Use separate catches when different failures need different recovery behavior.

## Question 13: Difference between throw and throws

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 21

The PDF distinguishes `throw` as explicitly throwing an exception object and `throws` as declaring possible exceptions in a method signature.

### Short Interview Answer

`throw` is used inside code to actually throw a particular `Throwable` object. `throws` appears in a method declaration and communicates that the method may allow one or more exceptions to propagate to its caller.

### throw

```java
if (age < 18) {
    throw new IllegalArgumentException(
            "Age must be 18 or above"
    );
}
```

Here we are actually creating/throwing an exception.

### throws

```java
void readFile() throws IOException {
    ...
}
```

Here we are saying:

This method may let `IOException` escape.

Caller must deal with it.

### Comparison

| throw | throws |
|---|---|
| Actually throws exception | Declares possible propagation |
| Used inside method/block | Used in method signature |
| Followed by throwable expression/object | Followed by exception type(s) |
| One object thrown at that instant | Can declare multiple exception types |

Example:

```java
void process()
        throws IOException, SQLException {
}
```

### ⚠️ Important Clarification from the PDF

The PDF says throw propagates only unchecked exceptions while throws can propagate checked and unchecked exceptions.

Do not memorize that literally.

You can absolutely write:

```java
throw new IOException();
```

A checked exception can be explicitly thrown with `throw`; it simply must be caught or declared appropriately.

For example:

```java
void test() throws IOException {
    throw new IOException("Failed");
}
```

Correct mental model:

```
throw
→ performs the throwing

throws
→ declares that an exception may leave the method
```

## Question 14: What is exception propagation?

**Priority:** 🔥 Must Know | 🧠 Deep Understanding
**Source:** 📘 PDF Question 21

The PDF explains propagation through a method chain such as:

```
m1()
 ↓
m2()
 ↓
m3()
```

If `m3()` throws an exception and doesn't handle it, control moves back through callers until a handler is found or the exception remains uncaught.

### Example

```java
static void method3() {
    throw new RuntimeException("Failure");
}

static void method2() {
    method3();
}

static void method1() {
    method2();
}
```

Call stack:

```
main()
  ↓
method1()
  ↓
method2()
  ↓
method3()
  ↓
RuntimeException
```

Now stack unwinding begins:

```
method3 ❌ no handler
       ↑
method2 ❌ no handler
       ↑
method1 ❌ no handler
       ↑
main    ✅ maybe catch
```

### Example

```java
public static void main(String[] args) {

    try {
        method1();
    } catch (RuntimeException e) {
        System.out.println("Handled");
    }
}
```

Output:

```
Handled
```

## Question 15: What does stack unwinding mean?

**Priority:** ⭐ Important

When an exception leaves a method, that method's normal execution cannot continue.

Its stack frame begins to unwind, and control moves toward its caller.

Conceptually:

```
Call stack before exception:

| method3 |
| method2 |
| method1 |
| main    |


Exception thrown in method3

      ↓

method3 frame exits
method2 frame exits
method1 frame exits

until matching handler found
```

That's the runtime mechanism behind exception propagation.

## Question 16: What are exception rules during method overriding?

**Priority:** 🔥🔥 Must Know | ⚠️ Tricky
**Source:** 📘 PDF Question 22

The PDF summarizes:

- if parent method declares no checked exception, child override cannot introduce a checked exception;
- it may introduce unchecked exceptions;
- if the parent declares a checked exception, the child may declare none, the same exception, or a narrower checked exception, but not a broader one.

### Case 1 — Parent Declares No Checked Exception

```java
class Parent {

    void process() {
    }
}
```

Child cannot do:

```java
class Child extends Parent {

    @Override
    void process() throws IOException {
    }
}
```

Compile-time error.

### Why?

Polymorphism.

Imagine:

```java
Parent p = new Child();

p.process();
```

The caller sees:

```
Parent.process()
```

which promised:

```
No checked exception requirement.
```

If runtime `Child.process()` suddenly introduced:

```
IOException
```

the caller would be forced to handle something the parent's contract didn't advertise.

That would break substitutability.

### Case 2 — Parent Declares Checked Exception

```java
class Parent {

    void process() throws IOException {
    }
}
```

Child may declare the same:

```java
@Override
void process() throws IOException {
}
```

or narrower:

```java
@Override
void process()
        throws FileNotFoundException {
}
```

or none:

```java
@Override
void process() {
}
```

But not broader:

```java
@Override
void process() throws Exception {
}
```

The PDF visually walks through these same variants across pages 42–46.

### Unchecked Exceptions

An overriding method can introduce unchecked exceptions:

```java
@Override
void process()
        throws IllegalArgumentException {
}
```

because callers aren't compiler-required to catch runtime exceptions.

## Question 18: What if finally also contains return?

**Priority:** 🔥 Must Know | ⚠️ Dangerous

The PDF shows:

```java
try {
    return 1;
} catch (Exception e) {
    return 2;
} finally {
    return 3;
}
```

and the result is:

```
3
```

Why?

The `finally` completion replaces the pending return from `try`.

```
try:
pending return 1
       ↓
finally executes
       ↓
return 3
       ↓
final result = 3
```

### Interview Rule

Do not return from `finally`.

It makes flow confusing and can suppress both:

```
earlier return values
```

and

```
exceptions
```

## Question 19: What is unreachable code?

**Priority:** ⭐ Important | ⚠️ Output Question

The PDF demonstrates that code placed after an unconditional `return` or `throw` may cause a compile-time unreachable-code error.

Example:

```java
return 1;

System.out.println("Hello");
```

The second statement can never execute.

Compile-time error.

Similarly:

```java
throw new RuntimeException();

System.out.println("Hello");
```

also has unreachable code.

## Question 20: What happens when an exception is thrown from finally?

**Priority:** 🔥🔥 Must Know | ⚠️ Very Tricky
**Source:** 📘 PDF Question 26

The PDF states that an exception thrown by `finally` takes precedence over an earlier exception thrown from `try`/`catch`.

### Example

```java
try {
    throw new IllegalArgumentException("TRY");

} finally {
    throw new RuntimeException("FINALLY");
}
```

The escaping exception is:

```
RuntimeException: FINALLY
```

The original failure can become hidden/suppressed by this control flow.

That's one major reason throwing or returning directly from `finally` is dangerous.

## Question 22: How do we create a custom exception?

**Priority:** 🔥 Must Know | 💻 Coding
**Source:** 📘 PDF Questions 24–25

The PDF explains that custom checked exceptions extend `Exception`, while custom unchecked exceptions extend `RuntimeException`.

### Custom Checked Exception

```java
class InsufficientBalanceException
        extends Exception {

    public InsufficientBalanceException(
            String message) {

        super(message);
    }
}
```

Use:

```java
void withdraw(double amount)
        throws InsufficientBalanceException {

    if (amount > balance) {
        throw new InsufficientBalanceException(
                "Insufficient balance"
        );
    }
}
```

### Custom Unchecked Exception

```java
class UserNotFoundException
        extends RuntimeException {

    public UserNotFoundException(
            String message) {

        super(message);
    }
}
```

Use:

```java
if (user == null) {
    throw new UserNotFoundException(
            "User not found"
    );
}
```

## Question 23: When should we create a custom exception?

**Priority:** 🔥 Important | 🧠 Practical

Custom exceptions make failures communicate business meaning.

Instead of:

```java
throw new RuntimeException();
```

use:

```java
throw new RideNotFoundException();
```

or:

```java
throw new InvalidBookingStateException();
```

Now:

```
technical failure representation
           ↓
expresses business problem
```

### Spring Boot Example

Service:

```java
public User getUser(Long id) {

    return repository.findById(id)
            .orElseThrow(() ->
                    new UserNotFoundException(
                            "User not found: " + id
                    ));
}
```

Controller advice:

```java
@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<?> handle(
        UserNotFoundException ex) {

    return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(ex.getMessage());
}
```

Flow:

```
Repository
   ↓
user missing
   ↓
Service throws
UserNotFoundException
   ↓
@ControllerAdvice catches
   ↓
HTTP 404
```

That's a very practical backend use of exception design.

## Question 25: What is try-with-resources?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 28

The PDF says try-with-resources was introduced in Java 7, automatically closes declared resources, and requires resources to implement `AutoCloseable`.

### Short Interview Answer

Try-with-resources is a Java construct for safely managing resources such as files, streams, or JDBC objects. A resource implementing `AutoCloseable` can be declared in the `try` header, and Java automatically closes it when execution leaves the block, including when an exception occurs.

### Before Try-With-Resources

Historically:

```java
FileInputStream input = null;

try {
    input = new FileInputStream("data.txt");

} finally {

    if (input != null) {
        input.close();
    }
}
```

Problems:

- verbose
- easy to forget close()
- cleanup itself may throw
- multiple resources get complicated

### With Try-With-Resources

```java
try (FileInputStream input =
             new FileInputStream("data.txt")) {

    // use input
}
```

Conceptually:

```
open resource
     ↓
use resource
     ↓
exception or normal completion
     ↓
automatic close()
```

### Multiple Resources

```java
try (
    Connection connection = getConnection();
    PreparedStatement ps =
            connection.prepareStatement(sql)
) {

    // execute SQL
}
```

Resources are closed automatically.

### Important Follow-Up: In What Order Are Resources Closed?

If:

```java
try (
    ResourceA a = new ResourceA();
    ResourceB b = new ResourceB();
) {
}
```

they are closed in reverse creation/declaration order:

```
B closes first
A closes second
```

Think stack-like cleanup.

## Question 26: What happens if both the try body and resource closing throw exceptions?

**Priority:** 🧠 Deep Understanding | ⚠️ Tricky

This is one important advantage of try-with-resources.

Suppose:

```
Main operation throws Exception A

then

close() throws Exception B
```

Java preserves the main exception:

```
Exception A
```

and attaches:

```
Exception B
```

as a suppressed exception.

You can inspect them:

```java
exception.getSuppressed();
```

This is much better than accidentally losing the original failure during cleanup.

## Question 27: Should we catch Exception everywhere?

**Priority:** 🔥 Interview Judgment

Usually:

```java
catch (Exception e)
```

everywhere is a poor design.

Why?

You lose specificity:

```
File not found
Database failure
Invalid input
Authentication failure
```

all collapse into:

```
Something failed
```

Better:

```java
catch (IOException e) {
    ...
}
```

when you know how to handle I/O failure.

At architectural boundaries, broad exception handling can be appropriate—for example a global Spring Boot exception handler—but lower-level code should generally preserve meaningful failure information.

## Question 28: Should we swallow exceptions?

**Priority:** 🔥 Important | ⚠️ Common Fresher Mistake

Never do this casually:

```java
try {
    repository.save(user);

} catch (Exception e) {
}
```

Now:

```
Database operation fails
        ↓
exception disappears
        ↓
caller thinks nothing happened
        ↓
debugging nightmare
```

If catching, you should usually:

```
recover
OR
translate
OR
log appropriately and propagate
OR
return meaningful failure at boundary
```

## Question 29: getMessage() vs printStackTrace()

**Priority:** ⭐ Important

Suppose:

```java
catch (Exception e) {
}
```

**e.getMessage()**

Returns the exception's descriptive message.

**e.printStackTrace()**

Prints stack trace information showing the path through which the exception propagated.

Conceptually:

```
getMessage()
→ what happened?

stack trace
→ where/how did execution reach the failure?
```

In production backend code, proper logging frameworks are generally preferred over arbitrary `printStackTrace()` calls.

## Exception Handling Mental Model

```
               Operation
                    |
                    v
             Something fails
                    |
                    v
              Exception object
```

## Common Fresher Mistakes

**❌ 1. "Checked exceptions happen at compile time."**

Wrong.

The compiler checks the handling requirement at compile time.

The actual exception still occurs at runtime.

**❌ 2. "Unchecked means we cannot catch it."**

Wrong.

You can:

```java
catch (NullPointerException e)
```

The compiler simply doesn't force you to.

**❌ 3. "Error can never be caught."**

Too absolute.

Better:

Errors generally shouldn't be treated as ordinary recoverable application conditions.

**❌ 4. "throw is only for unchecked exceptions."**

Wrong.

```java
throw new IOException();
```

is legal provided checked-exception rules are satisfied.

**❌ 5. "throws throws the exception."**

No.

```
throw  → actually throws

throws → declares potential propagation
```

**❌ 6. "finally always executes."**

Too absolute.

JVM/process termination can prevent it.

**❌ 7. "return from finally is okay."**

Avoid it.

It can replace:

```
return values
exceptions
```

**❌ 8. "Catch Exception first."**

Wrong when specific catches follow.

```
Specific → General
```

**❌ 9. "try-with-resources works with any object."**

No.

The resource must satisfy the appropriate automatic-close contract; the PDF explicitly calls out `AutoCloseable`.

## Interviewer Grill Round — Exceptions

**Interviewer**
What is an exception?

**Candidate**
An exception is an object representing an abnormal condition that interrupts normal execution. Java allows us to handle it locally or propagate it to a caller that can deal with the failure.

**Interviewer**
What's the root class for exceptions?

**Candidate**
`Throwable` is at the root of Java's throwable hierarchy, with major branches `Error` and `Exception`.

**Interviewer**
Error vs Exception?

**Candidate**
Exceptions generally represent failures applications may reasonably anticipate or handle. Errors normally represent serious JVM/runtime conditions that ordinary application code is generally not expected to recover from.

**Interviewer**
Checked vs unchecked?

**Candidate**
Checked exceptions must be caught or declared by the compiler. Unchecked exceptions are `RuntimeException` subclasses and don't have that compiler requirement.

**Interviewer**
Does that mean checked exceptions occur at compile time?

**Candidate**
No. The compiler checks whether we've handled or declared them at compile time; the exception itself occurs at runtime.

**Interviewer**
Can we write try without catch?

**Candidate**
Yes, when it's followed by `finally`. A bare `try` block isn't valid.

**Interviewer**
Can we write:
```java
catch (Exception e) {
}

catch (IOException e) {
}
```

**Candidate**
No. `IOException` is already covered by `Exception`, so the second catch is unreachable. More-specific exceptions must appear before broader ones.

**Interviewer**
Difference between throw and throws?

**Candidate**
`throw` actually throws a particular `Throwable` object from code. `throws` declares in a method signature that exceptions may propagate to the caller.

**Interviewer**
Can throw throw a checked exception?

**Candidate**
Yes. For example, `throw new IOException(...)` is legal, but the method must catch it or declare it because `IOException` is checked.

**Interviewer**
What is exception propagation?

**Candidate**
If a method doesn't handle an exception, it can propagate up the call stack to its caller. Stack frames unwind until a matching handler is found or the exception remains uncaught.

**Interviewer**
Parent method:
```java
void test() {}
```
Can child write:
```java
void test() throws IOException {}
```

**Candidate**
No. An override cannot introduce a new broader checked-exception obligation that the parent method didn't declare.

**Interviewer**
Parent declares:
```java
void test() throws IOException
```
Can child declare:
```java
void test() throws FileNotFoundException
```

**Candidate**
Yes. `FileNotFoundException` is narrower than `IOException`.

**Interviewer**
What happens here?
```java
try {
    return 1;
} finally {
    return 2;
}
```

**Candidate**
The method returns 2, because the finally return replaces the pending return from try. Returning from finally is therefore strongly discouraged.

**Interviewer**
What if try throws Exception A and finally throws Exception B?

**Candidate**
The exception from finally becomes the one that escapes that control flow, potentially hiding the original exception.

**Interviewer**
Then how does try-with-resources improve this?

**Candidate**
It automatically closes `AutoCloseable` resources and, if both the operation and `close()` fail, it preserves the primary exception and records cleanup failures as suppressed exceptions.

**Interviewer**
Why create custom exceptions?

**Candidate**
To express meaningful domain-specific failures such as `UserNotFoundException` or `InsufficientBalanceException` rather than exposing generic exceptions without business meaning.
