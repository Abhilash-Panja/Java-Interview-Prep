## Question 1: What is String in Java?

**Priority:** 🔥 Must Know
**Source:** ➕ Added foundation

**Difficulty:** Beginner
**Interview Frequency:** Very High

### What the Interviewer Is Testing

Whether you understand that `String` is an object, not a primitive, and that it has special language/runtime support.

### Short Interview Answer

`String` is a class from `java.lang` used to represent a sequence of characters. String objects are immutable, meaning their value cannot change after creation. Java also gives Strings special support through string literals and the String Pool, which allows identical literals to be reused.

Example:

```java
String name = "Abhilash";
```

String is a class.

This is therefore an object reference:

```
name
  |
  v
String object
"Abhilash"
```

It is not a primitive like:

```
int
double
boolean
```

## Question 2: How many ways can we create a String?

**Priority:** 🔥 Must Know | ⚠️ Common Fresher Question
**Source:** ➕ Added

### Short Interview Answer

The two most commonly discussed interview approaches are using a String literal and using the `new String(...)` constructor. The important difference is that literals participate directly in the String Pool, while explicitly using `new` creates a distinct String object.

### Method 1 — String Literal

```java
String s1 = "Java";
```

### Method 2 — new

```java
String s2 = new String("Java");
```

There are of course other constructors, such as creating Strings from character or byte data:

```java
char[] chars = {'J', 'a', 'v', 'a'};

String s3 = new String(chars);
```

But for interview discussions, the important comparison is usually:

```
"Java"
vs
new String("Java")
```

## Question 3: What is the String Pool?

**Priority:** 🔥🔥 Must Know | 🧠 Deep Understanding
**Source:** 📘 PDF + expansion

The PDF describes the String Pool as a special area associated with Java heap storage where existing pooled Strings can be reused instead of creating another identical String object.

### Short Interview Answer

The String Pool is a JVM-managed pool of canonical Strings. When Java uses a String literal, it can reuse an existing pooled String with the same content rather than maintaining separate identical String objects. This reduces unnecessary duplication, and String immutability makes that sharing safe.

### Root Cause

Consider:

```java
String s1 = "Java";
String s2 = "Java";
String s3 = "Java";
```

Without pooling, conceptually:

```
s1 → "Java"
s2 → "Java"
s3 → "Java"
```

Three identical objects could waste memory.

Instead:

```
String Pool

        "Java"
          ^
       /  |  \
      /   |   \
    s1   s2   s3
```

All can reuse the same pooled String.

### Why Is Immutability Important for Pooling?

Imagine String were mutable:

```java
String s1 = "Java";
String s2 = "Java";
```

Both references might share:

```
        "Java"
          ^
         / \
       s1   s2
```

Now imagine:

```
s1 changes "Java" → "Python"
```

Then what should happen to `s2`?

If the shared object itself were modified:

```
s1 → "Python"
s2 → "Python"   ❌
```

even though `s2` never requested a change.

This is one of the PDF's principal explanations for String immutability.

## Question 4: String literal vs new String()

**Priority:** 🔥 Must Know | ⚠️ Tricky
**Source:** ➕ Added

Consider:

```java
String s1 = "Java";
String s2 = "Java";

String s3 = new String("Java");
```

Conceptually:

```
               String Pool
                   "Java"
                  ^      ^
                 /        \
               s1          s2


s3 ──────────────► separate String object
                    containing "Java"
```

Therefore:

```java
System.out.println(s1 == s2);
```

usually:

```
true
```

because the literals refer to the same pooled String.

But:

```java
System.out.println(s1 == s3);
```

is:

```
false
```

because `new String(...)` creates a distinct object.

And:

```java
System.out.println(s1.equals(s3));
```

is:

```
true
```

because their contents match.

### Famous Interview Trap: How Many Objects Are Created?

```java
String s = new String("Java");
```

Freshers often memorize:

"Always two objects."

That answer is too absolute.

A stronger answer is:

`new String("Java")` creates a new String object for the explicit `new`. The literal `"Java"` also refers to a pooled String, but that pooled String may already exist. So I wouldn't blindly say two new objects are always created at that exact statement.

That's a safer interview answer.

## Question 5: What is the difference between == and equals() for String?

**Priority:** 🔥🔥 Must Know | ⚠️ Extremely Common
**Source:** 📘 PDF Question 30 + expansion

The PDF states that `String` overrides `Object.equals()` so that String equality compares String contents.

### Short Interview Answer

For String references, `==` checks whether both references point to the same String object, while `equals()` compares the character content because `String` overrides `Object.equals()`.

Example:

```java
String s1 = "Java";
String s2 = "Java";
String s3 = new String("Java");
```

Now:

```
s1 == s2
→ true

s1 == s3
→ false

s1.equals(s3)
→ true
```

### Mental Model

```
==
 |
 └── Are these the SAME object?

equals()
 |
 └── Do these Strings contain the SAME characters?
```

### Common Fresher Mistake

Don't say:

"== compares references and equals() always compares values."

That's too generic.

Correct:

`equals()` does whatever the class implementation defines.

For String, that happens to mean content comparison.

This distinction becomes important later because the PDF shows that `StringBuilder` does not behave like `String` here.

## Question 6: What does immutable mean?

**Priority:** 🔥 Must Know

### Short Interview Answer

An immutable object is one whose observable state cannot be changed after the object has been created. Operations that appear to modify an immutable String actually produce or return another String rather than modifying the original String object.

Example:

```java
String s = "Java";

s.concat(" Developer");
```

What is `s`?

Still:

```
Java
```

because the original String wasn't modified.

To use the result:

```java
s = s.concat(" Developer");
```

Now:

```
Java Developer
```

The reference changed to another result.

Conceptually:

```
Before:

s ─────► "Java"


concat(" Developer")


        "Java"             "Java Developer"
                            ^
                            |
                            s
```

The original `"Java"` object itself wasn't changed.

## Question 7: Why is String immutable in Java?

**Priority:** 🔥🔥 Must Know | 🧠 Deep Understanding
**Source:** 📘 PDF Question 29

This is one of the strongest questions in the PDF.

The PDF gives five reasons:

- String Pool
- Security
- Multithreading
- Hash-code caching / Map keys
- Class loading usage

### Short Interview Answer

String immutability makes String Pool sharing safe, makes Strings naturally safe to share between threads, keeps their hash behavior stable for hash-based collections, and prevents String values from unexpectedly changing after being passed around. These properties are especially useful because Strings are used everywhere for identifiers, paths, configuration values, class names, URLs, and map keys.

Now understand each reason.

### Reason 1 — String Pool

As discussed:

```java
String a = "Java";
String b = "Java";
```

can safely share:

```
      "Java"
       /    \
      a      b
```

because nobody can mutate that shared String.

The PDF makes this its first reason for immutability.

### Reason 2 — Security / Stable Values

Strings are commonly used to represent things such as:

- database URLs
- file paths
- network host names
- class names
- usernames
- configuration values

The PDF specifically connects immutability to network connections, database URLs, usernames, and passwords.

The core reasoning is:

Once a String value is supplied, another reference cannot mutate that same String object underneath you.

### Reason 3 — Thread Safety

Because an existing String cannot be modified:

```
Thread 1 ──┐
           ├──► "Java"
Thread 2 ──┤
           │
Thread 3 ──┘
```

all threads can safely read that same String value without synchronizing access to mutations on that String.

The PDF explicitly calls String implicitly thread-safe because of immutability.

Important nuance:

This doesn't mean every application containing Strings is automatically thread-safe.

It means the String object's value itself cannot suffer a mutation race.

### Reason 4 — Stable hashCode() / Good HashMap Key

This connects directly to our previous module.

Suppose:

```java
Map<String, User> users = new HashMap<>();

users.put("abhilash", user);
```

If `"abhilash"` could mutate after being inserted:

```
Before:

"abhilash"
   ↓
hash = H1
   ↓
bucket B1


After mutation:

"rahul"
   ↓
hash = H2
```

The map entry would have been stored based on the old hash state.

That is dangerous.

With String:

```
value cannot change
        ↓
equality-significant content stable
        ↓
hash remains stable
        ↓
excellent HashMap key
```

The PDF explicitly connects String immutability with hash-code caching and suitability as a Map key.

### Reason 5 — Class Loading

The PDF also notes that Strings are used by Java class-loading infrastructure and connects their immutability with stable/security-sensitive naming.

For fresher interviews, the first four reasons are generally more important to explain confidently.

## Question 8: Is String immutable only because the class is final?

**Priority:** 🔥 Must Know | ⚠️ Counter Question
**Source:** ➕ Added

No.

This connects back to Module 1.

A `final` class means:

```
cannot be subclassed
```

It does not automatically mean:

```
immutable
```

For example:

```java
final class Person {

    String name;

    void setName(String name) {
        this.name = name;
    }
}
```

The class is final.

But:

```java
person.setName("Rahul");
```

changes its state.

So:

```
final class
      ≠
immutable class
```

For immutability, state must not be externally changeable.

## Question 9: What happens when we concatenate Strings?

**Priority:** 🔥 Important | 🧠 Deep Understanding
**Source:** ➕ Added

Example:

```java
String s = "Java";

s = s + " Developer";
```

Because Strings are immutable:

```
"Java"
```

is not modified in place.

A resulting String value representing:

```
"Java Developer"
```

is produced.

### Compile-Time Constants

Consider:

```java
String s1 = "Java" + "Developer";
String s2 = "JavaDeveloper";

System.out.println(s1 == s2);
```

Because both operands are compile-time constants, the compiler can fold:

```
"Java" + "Developer"
```

into:

```
"JavaDeveloper"
```

So this comparison can be:

```
true
```

### Runtime Concatenation

Consider:

```java
String first = "Java";

String result = first + " Developer";
```

This must be produced at runtime.

You should understand the conceptual rule:

```
String is immutable
      ↓
original isn't modified
      ↓
a resulting String is produced
```

The compiler/JVM may optimize how concatenation is implemented, so don't rigidly tell an interviewer that every `+` is always translated into one specific `StringBuilder` sequence in every modern Java version.

## Question 10: Why shouldn't we repeatedly concatenate Strings in a loop?

**Priority:** 🔥 Important | 💻 Coding

Consider:

```java
String result = "";

for (int i = 0; i < 10000; i++) {
    result = result + i;
}
```

Conceptually, because String is immutable, repeated concatenation can require many intermediate String results.

Better:

```java
StringBuilder result = new StringBuilder();

for (int i = 0; i < 10000; i++) {
    result.append(i);
}

String finalResult = result.toString();
```

Why?

`StringBuilder` is mutable:

```
String
"Java"
  ↓ modification
new String required


StringBuilder
buffer
  ↓
modify same builder state
```

## Question 11: What is intern()?

**Priority:** ⭐ Important | ⚠️ Tricky
**Source:** ➕ Added — I did not find a dedicated `intern()` question in the PDF; the PDF discusses the String Pool only inside the immutability answer.

### Short Interview Answer

`intern()` returns the canonical pooled representation of a String. If an equal String is already present in the String Pool, its pooled reference is returned; otherwise a canonical pooled representation is established and returned.

Example:

```java
String s1 = new String("Java");
String s2 = s1.intern();
String s3 = "Java";
```

Then:

```java
System.out.println(s1 == s3);
```

→ `false`

but:

```java
System.out.println(s2 == s3);
```

→ `true`

Conceptually:

```
s1 ─────► separate "Java"

String Pool:
          "Java"
          ^    ^
          |    |
         s2   s3
```

## Question 12: What are StringBuilder and StringBuffer?

**Priority:** 🔥 Must Know
**Source:** 📘 PDF Question 31

The PDF explains that both are mutable classes for String manipulation, while `StringBuffer` provides synchronization/thread-safety and `StringBuilder` is preferred when that synchronization is unnecessary.

### Short Interview Answer

`StringBuilder` and `StringBuffer` are mutable character-sequence classes used when we need to modify text repeatedly. `StringBuilder` is generally preferred in ordinary single-threaded/local usage because it doesn't provide the synchronization overhead of `StringBuffer`. `StringBuffer` provides synchronized operations for scenarios requiring that style of thread-safe access.

### String Example

```java
String s = "Java";

s.concat(" Developer");
```

Original unchanged.

### StringBuilder Example

```java
StringBuilder builder =
        new StringBuilder("Java");

builder.append(" Developer");

System.out.println(builder);
```

Output:

```
Java Developer
```

The same builder object is modified.

Conceptually:

```
builder
   |
   v
"Java"
   |
 append(...)
   v
"Java Developer"

same builder object
```

### StringBuffer

Usage looks similar:

```java
StringBuffer buffer =
        new StringBuffer("Java");

buffer.append(" Developer");
```

The main distinction emphasized by the PDF is synchronization/thread-safety.

## Question 14: Does StringBuilder.equals() compare contents?

**Priority:** 🔥 Must Know | ⚠️ PDF Interview Trap
**Source:** 📘 PDF Question 32

The PDF shows:

```java
StringBuilder sb1 =
        new StringBuilder("hello");

StringBuilder sb2 =
        new StringBuilder("hello");
```

and the program outputs:

```
Not Equal
```

because `StringBuilder` does not override `equals()` with String-like content semantics; `Object`-style equality behavior therefore applies.

### Example

```java
StringBuilder a =
        new StringBuilder("Java");

StringBuilder b =
        new StringBuilder("Java");

System.out.println(a.equals(b));
```

Output:

```
false
```

because:

```
a ─────► StringBuilder #1

b ─────► StringBuilder #2
```

### But Their Contents Look the Same!

Correct.

If you want to compare their resulting text as Strings:

```java
a.toString().equals(b.toString())
```

would compare String contents.

### Why Are StringBuilder and StringBuffer Poor HashMap Keys?

The PDF explicitly links their mutability with their poor suitability as hash keys.

This connects perfectly to Module 3:

```
HashMap key
    ↓
equality/hash behavior should remain stable

StringBuilder
    ↓
mutable

Therefore
    ↓
usually poor key choice
```

## Question 15: Which should I use in real code?

**Priority:** 🔥 Must Know

### Use String

When the value represents stable text:

```java
String username;
String endpoint;
String message;
String email;
```

### Use StringBuilder

When constructing or modifying text repeatedly:

```java
StringBuilder query =
        new StringBuilder();

query.append("SELECT ");
query.append("* ");
query.append("FROM users");
```

Particularly for local computation.

### Use StringBuffer

When you specifically require the synchronization semantics it provides.

Don't automatically choose it just because the application has multiple threads.

A local builder inside a request-handling method may only be used by one thread:

```java
public String buildResponse() {

    StringBuilder builder =
            new StringBuilder();

    ...
}
```

In that situation, `StringBuilder` is normally sufficient.

## Common Fresher Mistakes

**❌ "String Pool means all Strings are automatically pooled."**

No.

String literals participate naturally in pooling. Objects explicitly created with `new String(...)` are distinct unless you obtain the canonical representation via `intern()`.

**❌ "String is immutable because it is final."**

Incomplete.

`final` prevents subclassing; immutability comes from the design preventing externally observable state changes.

**❌ "StringBuilder creates a new object on every append."**

No.

Its main purpose is mutable text construction.

**❌ "StringBuffer is always better because it is thread-safe."**

No.

Synchronization has a purpose and cost. Use it when the sharing model requires it.

**❌ "== should be used for String comparison because pooling makes references same."**

Never rely on pooling for logical String comparison.

Use:

```java
s1.equals(s2)
```

or null-safe alternatives depending on the situation.

## Interviewer Grill Round — Strings

**Interviewer**
What is String in Java?

**Candidate**
String is an immutable class from `java.lang` representing character sequences. Java also provides special support for String literals and maintains canonical pooled Strings for reuse.

**Interviewer**
How do you create Strings?

**Candidate**
The two common interview approaches are using a literal, such as `"Java"`, and explicitly using `new String("Java")`.

**Interviewer**
What's the difference?

**Candidate**
A literal uses the String Pool's canonical representation, while `new String(...)` creates a distinct String object.

**Interviewer**
What is the String Pool?

**Candidate**
It's a JVM-managed pool used to reuse canonical String values, especially literals, so identical values don't always need separate String objects.

**Interviewer**
Why is pooling possible safely?

**Candidate**
Because Strings are immutable. Multiple references can share one pooled String without one caller changing its value for everyone else.

**Interviewer**
```java
String a = "Java";
String b = "Java";
```
What is `a == b`?

**Candidate**
Typically true because both literals refer to the same pooled representation.

**Interviewer**
And what about:
```java
String a = "Java";
String b = new String("Java");

a == b
```

**Candidate**
False because `new String` creates a distinct object.

**Interviewer**
And `a.equals(b)`?

**Candidate**
True because String overrides `equals()` for content equality.

**Interviewer**
Why is String immutable?

**Candidate**
Important reasons include safe String Pool sharing, naturally safe sharing between threads, stable hash behavior for hash-based collections, and preventing shared String values from unexpectedly changing.

**Interviewer**
Why is immutability helpful for HashMap?

**Candidate**
Because fields used for equality and hashing don't change, so the String's hash/equality behavior remains stable after insertion as a key.

**Interviewer**
Is String immutable just because it's final?

**Candidate**
No. Final prevents subclassing. Immutability requires that the object's state cannot be changed after construction.

**Interviewer**
What happens here?
```java
String s = "Java";

s.concat(" Developer");

System.out.println(s);
```

**Candidate**
It prints `Java`. `concat()` doesn't mutate the existing String. The returned String would need to be assigned if I wanted to use the new value.

**Interviewer**
Why use StringBuilder?

**Candidate**
For repeated text modification or construction because it's mutable and avoids continually treating each modification as a change to an immutable String value.

**Interviewer**
StringBuilder vs StringBuffer?

**Candidate**
Both are mutable. StringBuffer provides synchronized operations, while StringBuilder doesn't, so StringBuilder is usually preferred for local/non-shared construction.

**Interviewer**
What does this print?
```java
StringBuilder s1 =
        new StringBuilder("Java");

StringBuilder s2 =
        new StringBuilder("Java");

System.out.println(s1.equals(s2));
```

**Candidate**
`false`, because StringBuilder doesn't override equals with String-style content equality.

**Interviewer**
Then how would you compare their textual contents?

**Candidate**
One straightforward approach is:
```java
s1.toString().equals(s2.toString())
```

**Interviewer**
What does intern() do?

**Candidate**
It returns the canonical pooled representation of a String, allowing an equal String to share the pooled reference.
