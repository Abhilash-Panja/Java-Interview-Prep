# Question 1: What is the JVM?

**Priority:** 🔥🔥 Must Know
**Source:** ➕ Expansion from Module 1

### Difficulty

Beginner

### Interview Frequency

Very High

### Short Interview Answer

> JVM stands for Java Virtual Machine. It provides the runtime environment that loads and verifies Java bytecode, manages runtime memory, executes code through interpretation and JIT compilation, manages threads, and performs garbage collection.

Think:

```text
Java Source
   ↓
javac
   ↓
Bytecode
   ↓
JVM
   ↓
Native execution
```

The JVM is therefore much more than:

> "Something that runs Java."

It includes several cooperating subsystems.

# Question 4: What is Heap memory?

**Priority:** 🔥🔥 Must Know

### Short Interview Answer

> The heap is the JVM-managed memory area where ordinary objects and arrays are allocated. It is shared by application threads and is the primary memory area managed by the garbage collector.

Example:

```java
Employee employee =
        new Employee();
```

Conceptually:

```text
Thread Stack

employee
   |
   | reference
   v

Heap

+------------------+
| Employee object  |
| id               |
| name             |
+------------------+
```

The PDF's garbage-collection chapter explicitly describes GC as examining heap memory and reclaiming unreachable objects.

# Question 5: What is Stack memory?

**Priority:** 🔥🔥 Must Know
**Source:** ➕ Added

### Short Interview Answer

> Every Java thread has its own JVM stack. A stack stores frames for active method invocations. Those frames contain information such as local variables, operand-stack data, and method-execution bookkeeping. When a method returns, its frame is removed.

Consider:

```java
public static void main(String[] args) {

    int x = 10;

    calculate(x);
}

static void calculate(int number) {

    int result = number * 2;
}
```

Conceptually:

```text
While calculate() executes:

Thread Stack

+-----------------------+
| calculate() frame     |
| number = 10           |
| result = 20           |
+-----------------------+
| main() frame          |
| x = 10                |
+-----------------------+
```

When `calculate()` returns:

```text
calculate frame removed
          ↓

+-----------------------+
| main() frame          |
| x = 10                |
+-----------------------+
```

# Question 6: Heap vs Stack

**Priority:** 🔥🔥🔥 Must Know | ⚠️ Classic Interview Question

### Short Interview Answer

> The heap is shared memory primarily used for objects and is managed by garbage collection. Each thread has its own JVM stack containing frames for active method calls. Stack frames are automatically pushed and popped as methods execute and return.

| Heap                                         | Stack                                                    |
| -------------------------------------------- | -------------------------------------------------------- |
| Shared between threads                       | One JVM stack per thread                                 |
| Objects/arrays generally allocated here      | Method frames                                            |
| GC-managed                                   | Frame lifetime follows method calls                      |
| Usually larger                               | Usually smaller                                          |
| Heap exhaustion can cause `OutOfMemoryError` | Excessive recursive depth can cause `StackOverflowError` |

---

# Important Fresher Trap

Do not memorize:

```text
primitives = stack
objects = heap
```

as an absolute rule.

A primitive can be:

```java
class User {
    int age;
}
```

Here `age` is part of the `User` object's state.

Conceptually:

```text
Heap:

User object
+----------+
| age = 25 |
+----------+
```

What matters is **context**.

You don't need JVM-spec byte-level detail for most fresher interviews, but understanding **one method call → one frame** is valuable.

# Question 14: What is Garbage Collection?

**Priority:** 🔥🔥🔥 Must Know
**Source:** 📘 PDF Question 69

### Short Interview Answer

> Garbage Collection is JVM-managed automatic memory reclamation. The collector identifies heap objects that are no longer reachable by the application and can reclaim their memory, so developers normally don't explicitly free Java objects.

The PDF defines GC as inspecting heap objects, identifying which are still in use and which are not, then reclaiming unused/unreferenced objects.

---

# Why Was Garbage Collection Needed?

In languages with explicit memory management, developers may need to manually release allocated memory.

That creates risks such as:

```text
forgetting to release memory
      ↓
leaks

releasing memory too early
      ↓
invalid access

releasing twice
      ↓
memory corruption
```

Java instead makes heap reclamation primarily the JVM's responsibility.

---

# Question 15: When is an object eligible for Garbage Collection?

**Priority:** 🔥🔥 Must Know

A beginner version is:

> When the object is no longer reachable by the running program.

The PDF describes unused objects as objects no longer referenced by the program.

But the deeper word is:

```text
REACHABLE
```

rather than simply:

```text
"has no variable pointing to it"
```

---

# Example 1

```java
Employee e =
        new Employee();

e = null;
```

Before:

```text
e ─────► Employee
```

After:

```text
e = null

Employee object
      ↑
no reachable reference path
```

Potentially GC-eligible.

---

# Example 2

```java
Employee e1 =
        new Employee();

Employee e2 = e1;

e1 = null;
```

Is the object GC-eligible?

No.

Because:

```text
e1 = null

e2 ─────► Employee
```

It is still reachable.

# Question 16: What are GC Roots?

**Priority:** 🔥 Important | 🧠 Deep Understanding
**Source:** ➕ Added — `GC roots` does not appear as a dedicated concept in the PDF search.

A more accurate reachability model is:

```text
GC Roots
   |
   +---- reachable object
             |
             +---- reachable object
                       |
                       +---- reachable object
```

Anything reachable through this graph remains alive.

Examples of root categories include things such as active-thread stack references and certain static/JVM-managed references.

Simplified:

```text
GC Root
  |
  v
Object A
  |
  v
Object B
  |
  v
Object C
```

All three stay alive.

But:

```text
Object X → Object Y
```

with no path from any root:

```text
GC eligible
```

even though X and Y reference each other.

---

# Tricky Counter Question

```java
class A {
    B b;
}

class B {
    A a;
}
```

Suppose:

```text
A ↔ B
```

but nothing reachable references either one.

Can GC reclaim them?

Yes.

Java GC is fundamentally reachability-based; circular references by themselves do not keep objects alive.


The general observation is:

```text
Most objects
     ↓

```

The PDF divides Young Generation into:

```text
Survivor S0
```

Conceptually:

```text
Young Generation

+-----------------------------+
| Eden                        |

+-----------------------------+
| Survivor 0 | Survivor 1     |
+-----------------------------+
```

Long-lived objects may eventually be promoted:


**Priority:** 🔥 Important

```text
       ↓

```

As Eden fills, a young-generation collection may occur depending on the collector.

# Question 19: What are Survivor spaces?

**Priority:** 🔥 Important

Objects surviving young-generation collection can be copied/moved between survivor areas as part of the collector's aging strategy.

The PDF describes a simplified cycle:

```text
Eden
 ↓
S0
 ↓
S1
 ↓
survive repeatedly
 ↓
Old Generation
```



For interviews, understand the purpose:

> Survivor spaces help track objects that survived young collections before they are eventually promoted.

Do not memorize a rigid object movement sequence as though every modern collector must implement it identically.

# Question 20: Minor GC vs Major GC vs Full GC

**Priority:** 🔥🔥 Important | ⚠️ Terminology Trap

The PDF uses:

```text
Minor GC
→ Young Generation

Major GC
→ Old Generation
```

and discusses stop-the-world behavior.

For interview purposes, be careful.

### Common conceptual usage

```text
Young / Minor collection
→ primarily young-generation reclamation
```

while broader old-generation or whole-heap collection terminology depends on the collector.

### Strong Interview Answer

> I use terms like young collection, old-generation collection, and full collection carefully because exact "major GC" semantics can vary between collectors and JVM documentation. The important concept is that young objects are collected frequently while longer-lived objects require different collection strategies.

That answer is safer than rigid memorization.

# Question 21: What is Stop-The-World?

**Priority:** 🔥🔥 Must Know

### Short Interview Answer

> A stop-the-world pause is a period where application threads are paused so the JVM can safely perform a particular GC or runtime operation.

Conceptually:

```text
Application Threads

T1 ████████ | STOP | ███████
T2 ████████ | STOP | ███████
T3 ████████ | STOP | ███████
                  ^
                  |
             GC pause
```

The PDF repeatedly uses stop-the-world terminology when explaining young and old-generation collection.

Modern collectors attempt to move substantial amounts of GC work concurrently with the application, but some phases still require pauses.

# Question 23: What is Serial GC?

**Priority:** ⭐ Important

### PDF framing

The PDF describes Serial GC as using a single GC execution thread and positioning it for relatively small workloads.

Conceptually:

```text
Application
   ↓ pause
Single GC worker
   ↓
collect
   ↓
Application resumes
```

Enable explicitly with:

```text
-XX:+UseSerialGC
```

The broad interview point:

> Simple collector, low complexity, suited to environments where single-threaded collection and pause behavior are acceptable.

# Question 24: What is Parallel GC?

**Priority:** 🔥 Important

The PDF describes Parallel GC as using multiple GC threads to improve throughput and notes that it prioritizes throughput while accepting application pauses.

Conceptually:

```text
Pause application
      ↓
+-----+-----+-----+
| GC1 | GC2 | GC3 |
+-----+-----+-----+
      ↓
collect faster using CPUs
      ↓
resume application
```

Main goal:

```text
Throughput
```

rather than ultra-low pause time.

# Question 25: What is CMS?

**Priority:** ⚠️ Historical / Modernization
**Source:** 📘 PDF + 🔄 modern correction

The PDF describes Concurrent Mark Sweep as a low-pause collector that performs substantial old-generation GC work concurrently with application threads.

That is useful historically.

## 🔄 Modern interview answer

Do not recommend CMS as a current collector.

The book reflects an older Java era. CMS was deprecated and later removed from modern HotSpot releases; a current interview should recognize it mainly as a **historical low-pause collector**.

So answer:

> CMS was an older concurrent low-pause collector. It is important historically, but it isn't a collector I would describe as a modern current choice.

# Question 26: What is G1 Garbage Collector?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF + modern expansion

The PDF describes G1 as a parallel/concurrent, incrementally compacting collector that divides the heap into regions and prioritizes regions containing more reclaimable garbage.

### Short Interview Answer

> G1, or Garbage-First, is a region-based generational garbage collector designed to balance throughput with predictable pause-time goals. It divides the heap into regions rather than relying purely on one fixed contiguous young/old layout and performs substantial work concurrently while some phases remain stop-the-world.

Current Oracle documentation describes G1 as generational, incremental, parallel, mostly concurrent, stop-the-world for some phases, and evacuating. ([Oracle Documentation][1])

---

# Why "Garbage First"?

Conceptually:

```text
Heap Regions

[R1 mostly live]
[R2 lots garbage]
[R3 mostly live]
[R4 lots garbage]
```

G1 can prioritize:

```text
R2
R4
```

where reclaiming space is especially worthwhile.

That's the intuition behind:

```text
Garbage First
```

# Question 31: Can Java still have memory leaks if it has Garbage Collection?

**Priority:** 🔥🔥🔥 Must Know
**Source:** ➕ Added — no dedicated `memory leak` section was found in the PDF.

Yes.

This is a very important question.

### Short Interview Answer

> Garbage Collection removes unreachable objects. A Java memory leak happens when objects are no longer useful to the application but remain reachable through references, so the collector cannot reclaim them.

Example:

```java
static List<byte[]> cache =
        new ArrayList<>();

while (true) {

    cache.add(
        new byte[1_000_000]
    );
}
```

Objects remain reachable through:

```text
static cache
```

So:

```text
GC Root
   ↓
static cache
   ↓
List
   ↓
byte[] objects
```

GC says:

```text
Still reachable.
Cannot reclaim.
```

Even though the application may no longer need them.

---

# Real Java Leak Sources

Typical examples include:

```text
Caches with no eviction
Static collections growing forever
Listeners never removed
ThreadLocal values not cleaned up correctly
ClassLoader retention
Resources retained through long-lived object graphs
```

The key principle is:

```text
GC reclaims unreachable memory,
not "memory the programmer no longer wants."
```

# Question 32: `OutOfMemoryError` vs `StackOverflowError`

**Priority:** 🔥🔥 Must Know

The PDF gives both as examples of serious Errors.

### `OutOfMemoryError`

Means the JVM couldn't satisfy a memory allocation in the relevant memory area.

Examples may involve:

```text
Java heap
Metaspace
native resources
```

depending on the specific error.

---

### `StackOverflowError`

Usually caused by excessive method-call depth, often infinite/unbounded recursion.

```java
void run() {
    run();
}
```

---

### Comparison

```text
OutOfMemoryError
→ memory allocation/resource exhaustion


StackOverflowError
→ thread stack exhausted
→ commonly too many nested calls
```

---

# Question 33: Does `OutOfMemoryError` always mean a memory leak?

**Priority:** 🔥 Important | ⚠️ Tricky

No.

It could result from:

```text
actual memory leak
heap too small
legitimate workload too large
huge allocation
too many retained objects
native memory pressure
excess class metadata
```

Therefore:

```text
OOM
≠ automatically memory leak
```

A memory leak is one possible cause.

# Question 34: What is a ClassLoader?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF Question 64

### Short Interview Answer

> A ClassLoader is responsible for locating/loading class definitions so classes can be used by the JVM. Java uses a delegation-oriented loader hierarchy where application class loading normally delegates toward parent loaders before trying to define the class itself.

The PDF describes a ClassLoader as loading `.class` definitions into memory when the program needs a class.

---

# Question 35: What class loaders does the PDF describe?

**Priority:** 🔥 Must Know | 🔄 Modernization

The PDF gives the older hierarchy:

```text
Bootstrap
   ↑
Extension
   ↑
System / Application
```

and says Bootstrap loads core classes from `rt.jar`, Extension loads extension-directory classes, and System/Application loads application classes from the classpath.

That describes the older pre-module runtime architecture.

---

# Modern ClassLoader Hierarchy

For a current interview:

```text
Bootstrap ClassLoader
        ↑
Platform ClassLoader
        ↑
System / Application ClassLoader
```

Oracle's current ClassLoader documentation describes these built-in loaders:

* Bootstrap
* Platform
* System/Application ([Oracle Documentation][4])

The old Extension ClassLoader was renamed/reworked as the **Platform ClassLoader** with the Java 9 module-system changes, and the old extension mechanism itself was removed. ([Oracle Documentation][5])

So do **not** answer a current interview with:

```text
Bootstrap
Extension
Application
```

without adding historical context.

# Question 36: What happened to `rt.jar`?

**Priority:** ⭐ Modern Awareness | ⚠️ PDF modernization

The PDF says Bootstrap loads JDK core classes from:

```text
jre/lib/rt.jar
```



That is an old-runtime description.

Starting with the modular JDK runtime introduced in Java 9, the old `rt.jar` model was removed; Java runtime classes are stored in the modular runtime image instead. Oracle's migration documentation explicitly notes that `rt.jar` and similar legacy jars were removed. ([Oracle Documentation][6])

# Question 37: What is parent delegation?

**Priority:** 🔥🔥 Must Know
**Source:** 📘 PDF

The PDF lists the **Delegation Principle**:

> A loader first forwards the class-loading request to its parent; if the parent cannot provide the class, the child gets a chance.

Conceptually:

```text
Application Loader
        |
        | request Employee
        v
Platform Loader
        |
        v
Bootstrap Loader
        |
      not found
        ↑
Platform
      not found
        ↑
Application
        |
        v
loads Employee
```

This helps avoid application code accidentally redefining fundamental platform classes through ordinary classpath loading.

Ask parent first.

### Visibility

Child loaders generally see classes visible from their parents, while the reverse isn't automatically true.

### Uniqueness

Parent delegation helps avoid unnecessarily loading the same class definition again lower in that delegation hierarchy.

For fresher interviews, the most important one is:

```text
Parent Delegation
```

# Question 41: What is class loading vs class initialization?

**Priority:** 🧠 Deep Understanding
**Source:** ➕ Added

Do not treat:

```text
load class
```

and:

```text
run all static initialization
```

as identical terms.

Conceptually, class lifecycle work includes stages such as:

```text
Loading
   ↓
Linking
   ↓
Initialization
```

Initialization is where class initialization logic such as static field initialization and static initializer blocks runs as required.

Example:

```java
class Demo {

    static int x = 10;

    static {
        System.out.println(
                "Static initialization"
        );
    }
}
```

The important fresher point is:

> ClassLoader loading and class initialization are related lifecycle steps, but "loading a class" is not simply synonymous with "running its constructor."

Constructors initialize objects, not class definitions.

> JIT stands for Just-In-Time compiler. The JVM can initially execute bytecode and gather runtime information, then compile frequently executed or performance-critical code paths into optimized native machine code so repeated execution becomes faster.

```text
   ↓

   ↓

   ↓

   ↓
JIT compiles
   ↓

```

# Real Spring Boot Memory Example

Suppose:

```java
@Service

    private final Map<Long, User> cache =
            new HashMap<>();
}
```

and the service continuously does:

```java

```

but never evicts anything.

Because:

```text

   ↓

   ↓
cache
   ↓
User objects
```

those objects remain reachable.

Therefore GC cannot say:


It only cares about reachability.

```text
eviction
size limits
expiration
```

independent of garbage collection.

# Common Fresher Mistakes

### ❌ 1. "Objects are stored in Stack."

Ordinary objects are generally heap allocated conceptually; local references may exist inside stack frames.

---

### ❌ 2. "All primitive variables are always on Stack."

Too absolute.

Primitive fields can be part of heap objects.

---

### ❌ 3. "GC deletes objects when their variable becomes null."

Not necessarily.

The object must become **unreachable**.

---

### ❌ 4. "Circular references cannot be garbage-collected."

Wrong.

```text
A ↔ B
```

can be reclaimed when neither is reachable from a GC root.

---

### ❌ 5. "Java cannot have memory leaks because it has GC."

Very wrong.

Reachable-but-unneeded objects can leak memory.

---

### ❌ 6. "System.gc() forces immediate GC."

Don't rely on it.

---

### ❌ 7. "GC closes files and database connections for us."

Do not design resource management around that assumption.

---

### ❌ 8. "PermGen and Metaspace are the same location."

No.

Metaspace replaced PermGen's class-metadata role and uses native memory.

---

### ❌ 9. "Extension ClassLoader is the current Java hierarchy."

Outdated.

Use:

```text
Bootstrap
Platform
Application
```

for modern interviews.

---

### ❌ 10. "Bootstrap loads everything from rt.jar."

Outdated modular-JDK explanation.

---

### ❌ 11. "Java is only interpreted."

Modern JVM execution includes JIT compilation.

---

### ❌ 12. "StackOverflowError means Heap is full."

No.

Stack overflow relates to thread-stack capacity, typically from excessive call depth.

# Interviewer Grill Round — JVM & Memory

## Interviewer

What is JVM?

### Candidate

JVM is the runtime environment that loads and verifies Java bytecode, manages runtime memory, executes code through mechanisms including interpretation and JIT compilation, manages threads, and performs garbage collection.

---

## Interviewer

What are the main JVM memory areas you know?

### Candidate

Heap, per-thread JVM stacks, class-metadata storage such as Metaspace in HotSpot, per-thread PC registers, and native method stacks.

---

## Interviewer

Heap vs Stack?

### Candidate

Heap is shared JVM-managed memory where ordinary objects and arrays live and is garbage-collected. Each thread has its own JVM stack containing frames for active method calls.

---

## Interviewer

What is inside a stack frame?

### Candidate

Conceptually it contains local-variable state, an operand stack for bytecode execution, and information associated with that method invocation.

---

## Interviewer

Where is this?

```java
Employee e =
        new Employee();
```

### Candidate

Conceptually the Employee object is allocated on the heap, while the local reference `e` exists in the current method's frame. JVM optimizations can complicate physical allocation, but that's the right interview mental model.

---

## Interviewer

What if I write:

```java
Employee e2 = e;
```

How many Employee objects?

### Candidate

One. The reference value is copied, so both variables refer to the same object.

---

## Interviewer

What is Garbage Collection?

### Candidate

Automatic JVM memory reclamation for heap objects that are no longer reachable from the application's live object graph.

---

## Interviewer

When is an object eligible for GC?

### Candidate

When it is no longer reachable through a path from GC roots.

---

## Interviewer

Two objects reference each other. Are they immortal?

### Candidate

No. If neither is reachable from a GC root, the entire cycle can still be collected.

---

## Interviewer

Then why can Java still have memory leaks?

### Candidate

Because GC only reclaims unreachable objects. If an object is no longer useful but is still reachable through something like a static collection or unbounded cache, GC must keep it.

---

## Interviewer

What is the Young Generation?

### Candidate

It's the generational area where newly allocated objects are generally handled. Many objects die young, so young-generation collection is optimized for frequent reclamation.

---

## Interviewer

Eden and Survivor spaces?

### Candidate

New objects are commonly allocated in Eden, and objects surviving young collections may be copied through survivor areas and eventually promoted when sufficiently long-lived.

---

## Interviewer

What is Stop-The-World?

### Candidate

A pause where application threads are stopped so the JVM can safely perform a GC or runtime phase requiring such coordination.

---

## Interviewer

What is G1?

### Candidate

G1 is a region-based generational collector designed to balance throughput with pause-time goals. It divides the heap into regions and performs a combination of concurrent and stop-the-world work.

---

## Interviewer

What about CMS?

### Candidate

CMS is historically important as an older concurrent low-pause collector, but it's no longer a modern collector choice.

---

## Interviewer

What is Metaspace?

### Candidate

HotSpot's native-memory-backed storage for class metadata introduced when PermGen was removed starting with Java 8.

---

## Interviewer

What is a ClassLoader?

### Candidate

A runtime component responsible for locating and defining classes. Java's standard loader model uses delegation so class-loading requests generally go toward parent loaders first.

---

## Interviewer

Name the class loaders.

### Candidate

For modern Java: Bootstrap, Platform, and System/Application ClassLoader.

---

## Interviewer

Extension ClassLoader?

### Candidate

That's older terminology. With Java 9's module-system changes the old Extension ClassLoader role was renamed/reworked as the Platform ClassLoader, and the old extension-directory mechanism was removed.

---

## Interviewer

Who loads `String`?

### Candidate

Core classes such as String are defined by bootstrap/platform runtime loading infrastructure; from `Class.getClassLoader()`, bootstrap-loaded classes are commonly represented with `null`.

---

## Interviewer

Why parent delegation?

### Candidate

It promotes consistent loading of platform classes and avoids ordinary child loaders redefining classes that a parent already provides.

---

## Interviewer

What is JIT?

### Candidate

Just-In-Time compilation lets the JVM compile frequently executed bytecode paths into optimized native machine code using runtime profiling information.

---

## Interviewer

Why might Java become faster after running for a while?

### Candidate

Because the JVM can identify hot methods and optimize them through JIT compilation after observing runtime behavior. That's part of JVM warm-up.

---

## Interviewer

`OutOfMemoryError` vs `StackOverflowError`?

### Candidate

OutOfMemoryError means the JVM couldn't satisfy a memory allocation in some relevant memory area. StackOverflowError usually means a thread exhausted its stack, often because of excessive recursion.

---

## Interviewer

Would you use GC for closing a database connection?

### Candidate

No. GC manages Java-memory reachability, while external resources need deterministic cleanup, normally through APIs such as AutoCloseable and try-with-resources.
